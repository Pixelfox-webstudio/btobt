# 견적·긴 입력 양식형 레퍼런스 기록 (quote-form)

본 날짜: 2026-11-17. 캡처는 모두 이 폴더에 있다. PC는 1440×900 창, 모바일은 390×844 창(배율 2, 저장 폭 780px)으로 찍었다.
로그인·회원가입·양식 제출은 하지 않았다. 넣어 본 값은 선택지 고르기, 수량 +1, 상품 담기, 나라 이름 앞 글자 "un"뿐이다.
색·글꼴·모서리·그림자는 기록하지 않았다(우리 DESIGN.md 값만 쓴다). 아래는 구조·흐름·조작 방식만 적는다.

## 1. 숨고 요청서 — 대화형 입력

- 주소: https://soomgo.com/hire/단체티셔츠-제작 (열면 `?from=일반 요청서`가 붙는다)
- 본 날짜: 2026-11-17
- 캡처: soomgo-quantity-pc.jpg, soomgo-quantity-m.jpg (세 번째 질문·진행률 60%), soomgo-edit-pc.jpg, soomgo-edit-m.jpg (첫 답의 "수정"을 누른 상태), soomgo-skip-m.jpg (네 번째 질문·건너뛰기 버튼), soomgo-thread-m.jpg (건너뛴 뒤 대화 전체 + 다섯 번째 질문)

관찰한 사실
- 화면 위쪽에 흰 띠가 고정된다. 띠 안에는 양식 이름("단체티셔츠 제작") + 정보 아이콘, 그 아래 가는 진행률 막대, 막대 오른쪽 끝에 % 숫자가 있다. 답할 때마다 0% → 46% → 60% → 69% → 77%로 올랐다(질문 수가 아니라 비율로만 보여 준다).
- 본문은 회색 바탕의 한 열이다(PC 폭 약 600px, 가운데). 맨 위에 안내 말풍선 한 개("몇 가지 정보만 알려주시면 평균 4개 이상의 견적을 받을 수 있어요.")가 있고 그 아래로 대화가 쌓인다.
- 답한 질문은 "질문 말풍선(왼쪽, 흰색) → 내 답 말풍선(오른쪽, 어두운 색) → 답 바로 아래 오른쪽 정렬 '수정' 링크" 세 줄 묶음으로 남는다.
- 지금 답할 질문만 흰 카드로 열린다(PC 폭 약 400px, 열의 왼쪽에 붙음). 카드 안 순서는 질문 문장 → 선택지 → 맨 아래 전체 폭 "다음" 버튼. "다음"은 답을 고르기 전에는 비활성(회색)이다. 선택지가 많으면 카드 높이는 그대로 두고 선택지 목록만 카드 안에서 스크롤된다(여섯 번째 선택지가 잘려 보인다).
- 선택지는 한 줄에 하나씩, 테두리 있는 전체 폭 줄(왼쪽 동그라미 + 글자)이다.
- 사이즈·수량 질문은 "사이즈 이름(왼쪽) + − 0 +(오른쪽)" 줄을 XS, S, M, L, XL, 2XL, 3XL, 그 외 8개 세로로 쌓았다. XS를 1로 올리고 넘어가니 답 말풍선에 "· XS 1"로 요약됐다.
- 선택 질문("문구 및 로고 인쇄를 원하시나요?")에는 카드 맨 아래에 "건너뛰기"(선 버튼, 왼쪽, 좁게)와 "다음"(오른쪽, 넓게)이 나란히 있다. 건너뛰기는 누르는 즉시 다음 질문으로 넘어가고, 답 자리에 "건너뛰기를 선택했어요." 말풍선과 "수정" 링크가 남는다.
- 납품 날짜는 달력을 바로 띄우지 않고 선택지로 먼저 묻는다("협의 가능해요 / 가능한 빨리 진행하고 싶어요 / 일주일 이내로 진행하고 싶어요 / 원하는 날짜가 있어요 / 기타").
- "수정"을 누르면 그 질문이 제자리에서 카드로 다시 열린다. 전에 고른 값이 선택된 채이고 "다음"이 활성이다. 그 아래 원래 답 말풍선은 남고 링크만 "수정 취소"로 바뀐다. 뒤에 답한 질문·답은 지워지지 않고 진행률도 그대로다(60%, 77%).
- 다섯 번째 질문까지 로그인 요구가 없었다.
- PC와 모바일 차이: PC는 사이트 메뉴가 위에 그대로 있고 그 아래에 양식 띠가 붙는다. 모바일은 사이트 메뉴가 사라지고 "← 뒤로 · 양식 이름(가운데) · 정보 아이콘" 한 줄 + 진행률 막대만 남는다. 카드와 말풍선 구조는 같고, 카드는 화면 폭의 약 3/4, 답 말풍선은 오른쪽 끝에 붙는다. 수량 줄의 −/+ 단추는 모바일에서 약 32px 정사각형이다.

우리가 가져올 것
- 위쪽 고정 띠(양식 이름 + 진행률 막대 + % 숫자). 이유: 스크롤로 대화가 길어져도 어디까지 왔는지 한 줄로 보인다.
- "질문 – 내 답 – 수정" 묶음으로 쌓는 방식과, 수정을 제자리에서 여는 방식(뒤 답 유지, "수정 취소" 제공). 이유: 구매 담당자가 수량·사이즈를 고치러 처음으로 돌아가지 않아도 된다.
- 선택 질문에만 "건너뛰기"를 "다음" 왼쪽에 두고, 건너뛴 사실도 답 줄로 남기는 것. 이유: 무엇을 비워 뒀는지 나중에 보이고 다시 채울 수 있다.
- 사이즈별 수량 줄(이름 + − 숫자 +)과 답 요약("· XS 1"처럼 0이 아닌 것만). 이유: 우리 상품도 사이즈별 수량이 핵심 입력이다.
- 납품 희망일을 선택지로 먼저 묻고 "원하는 날짜가 있어요"를 골랐을 때만 날짜 칸을 여는 순서. 이유: 날짜가 정해지지 않은 문의가 많다.

바꿔서 쓸 것
- 진행률을 %만 쓰지 않고 "3 / 8 · 38%"처럼 질문 수를 함께 적는다. 이유: 숨고는 첫 답에 46%가 올라 남은 양을 가늠하기 어려웠다. 우리 문구 규칙도 수치에 기준을 붙이게 되어 있다.
- 말풍선 색 구분(흰색/어두운 색) 대신 우리 값으로: 질문은 `.note` 바탕(#F5F5F6), 내 답은 검정 알약 또는 검정 글자 + 1px 선, 본문 바탕은 흰색. 이유: 홈이 흰 바탕·검정 잉크다.
- 수량 직접 입력을 허용한다(숫자 칸을 눌러 입력). 이유: 단체복은 사이즈당 수십~수백 벌이라 +를 반복해 누를 수 없다. 숨고 화면에서는 +/−만 눌러 봤다.
- 상품 반복: 한 상품의 질문 묶음이 끝나면 "상품을 하나 더 추가할까요? 추가 / 다음 단계로" 질문을 넣고, 추가하면 "상품 2" 구분 줄부터 같은 질문을 다시 쌓는다(숨고에는 없어서 MOJ의 "n of m" 제목 방식을 빌린다).

쓰지 않을 것
- 카드 안에서만 스크롤되는 선택지 목록. 이유: 잘린 선택지가 있는지 알기 어렵다. 선택지는 모두 펼친다.
- 양식 아래에 이어 붙은 서비스 소개·후기 목록. 이유: 우리 양식 화면에는 입력과 요약만 둔다.

## 2. LG전자 B2B 온라인 견적 — 한글 긴 양식

- 주소: https://www.lge.co.kr/kr/business/contents/estimate/online-estimate-newstep1.do
- 본 날짜: 2026-11-17
- 캡처: lg-estimate-form-pc.jpg (전체, 제품 카테고리 두 칸을 고른 상태), lg-estimate-form-m.jpg (위쪽 4500px 분량), lg-estimate-form2-m.jpg (그 아래: 약관 끝·버튼·안내 띠·푸터), lg-estimate-guide-pc.jpg, lg-estimate-guide-m.jpg ("안내 보기" 팝업)

관찰한 사실
- 단계는 한 화면 하나다. 위치 표시에 "STEP1 견적 문의 내용 작성"이라고만 쓰여 있고 본문에는 단계 표시가 없다.
- 정보 순서(PC): 제목 "견적 상담" + 설명 두 줄(가운데) → 홍보 배너 3개 → "제품 카테고리 선택" → "기업정보" → "설치 현장 정보"(업종, 주소, 제품문의) → "견적 상담을 위한 약관 동의" → 버튼 2개 → 안내 띠("제품 페이지에서 온라인견적 문의 버튼을 클릭하여… [안내 보기]").
- 제품 카테고리 선택은 회색 판 안의 3열 라디오다(제품 카테고리* → 상세 카테고리* → 타입). 앞 열을 고르면 다음 열 선택지가 채워진다. 판 오른쪽 위에 "선택초기화"가 있다. 고른 값은 아래 "제품문의" 묶음의 읽기 전용 칸(제품 카테고리 / 상세 카테고리 / 타입)에 그대로 다시 적힌다.
- 기업정보·설치 현장 정보는 2열 표 모양이다. 왼쪽 열(약 210px, 회색 바탕)에 라벨, 오른쪽 열에 입력 칸. 한 줄에 항목 하나다.
- 묶음 칸의 모양: 사업자등록번호는 입력 칸 + "검색" 버튼 + 아래 도움말("기업정보 검색을 통해 선택한 데이터는 자동 입력 됩니다."). 담당자명은 성·이름 2칸. 휴대전화번호는 "010 선택 − 칸 − 칸" 3칸. 이메일은 "아이디 칸 @ 도메인 칸 + 도메인 선택(직접입력…)" + 아래 도움말. 주소는 "우편번호(읽기 전용) + 주소찾기 버튼 / 주소(읽기 전용) / 상세 주소" 세 줄. 업종은 선택 2개가 나란히.
- 제품문의 묶음은 라벨 열 하나에 작은 라벨이 붙은 칸 8개(제품 카테고리, 상세 카테고리, 타입, 모델명, 구매시기 선택, 구매수량, 예산 선택, 추가 문의 사항)가 세로로 쌓인다.
- 필수 표시는 라벨 뒤 빨간 *이고, 표마다 아래에 "* 표시는 필수 입력 항목입니다." 한 줄이 있다. 선택 동의에는 "(선택)"이 붙는다.
- 약관 동의는 제목 줄 오른쪽에 "전체동의" 체크가 있고, 그 아래 동의 5개(필수 2, 선택 3)가 각각 "체크 + 제목" 줄과 본문 상자(높이 고정, 상자 안 스크롤)로 펼쳐져 있다. 이 묶음만 PC에서 약 2,000px를 차지한다.
- 맨 아래 버튼은 가운데 정렬 2개다: "온라인견적문의 내역 조회"(선 버튼) + "온라인견적 문의하기"(채운 버튼).
- "안내 보기"를 누르면 가운데 팝업이 뜬다. 제목 + 오른쪽 위 닫기(×), 아래로 "1. 제품 목록 페이지 / 2. 제품 상세 페이지…" 단계마다 왼쪽에 번호·제목·설명 두 줄, 오른쪽에 그 화면 그림을 둔 줄이 세로로 쌓인다.
- 오른쪽에 떠 있는 원형 바로가기 3개(사업자몰·뉴스레터 신청·견적상담)가 모바일에서는 배너와 섹션 제목을 가린다.
- PC와 모바일 차이: 표가 풀려 라벨이 칸 위로 올라가고 한 열이 된다. 섹션 제목은 전체 폭 어두운 띠가 된다. 3열 카테고리는 "제품 카테고리 → 상세 카테고리 → 타입" 순서로 세로로 쌓이고 "선택초기화"는 묶음 맨 아래 버튼으로 내려간다. 연락처 3칸과 이메일 3조각은 모바일에서도 한 줄을 유지한다(이메일은 칸 하나가 약 70px로 좁아진다). "전체동의"는 어두운 띠 안의 체크 한 줄이 되고, 약관 본문 상자는 높이가 절반쯤으로 줄어든다. 아래 버튼 2개는 반반으로 나란히 놓인다.
- 오류 표시는 확인하지 않았다(제출 버튼을 누르지 않았다).

우리가 가져올 것
- 묶음 순서: 무엇을 문의하는지(상품) → 누가(회사·담당자) → 어디로·언제(납품) → 동의 → 버튼. 이유: 상품을 먼저 고르면 뒤 칸(수량·시기)이 그 상품 기준으로 채워진다.
- 연락처 "국번 선택 − 4자리 − 4자리", 이메일 "아이디 @ 도메인 + 도메인 선택", "우편번호 + 주소찾기 버튼 / 주소 / 상세 주소"의 칸 나눔과, 모바일에서도 연락처 3칸을 한 줄로 유지하는 것. 이유: 우리 양식의 칸 구성과 같다.
- 검색으로 채워지는 칸 아래의 도움말 한 줄("검색으로 고르면 자동으로 입력됩니다" 식). 이유: 직접 쳐야 하는지 헷갈리지 않는다.
- 위에서 고른 상품 값이 아래 "문의 내용" 묶음에 읽기 전용으로 다시 보이는 것. 이유: 제출 전에 무엇을 문의하는지 한 번 더 보인다.
- 제출 버튼 옆의 "문의 내역 조회" 선 버튼. 이유: 이미 문의한 사람이 같은 화면에서 길을 찾는다(우리는 회원 전용이므로 로그인 안내와 묶는다).
- 안내 팝업의 줄 구성(번호·제목·설명은 왼쪽, 화면 그림은 오른쪽, 단계마다 한 줄). 이유: 견적문의 안내 화면의 "진행 순서"에 그대로 쓸 수 있다.

바꿔서 쓸 것
- PC의 "회색 라벨 열 + 입력 열" 표 대신 우리 `.fld`(라벨 위, 칸 아래)를 쓴다. 이유: LG도 모바일에서는 라벨을 위로 올린다. 한 가지 모양으로 PC·모바일을 같이 쓴다.
- 이메일은 모바일에서 두 줄로 나눈다(첫 줄 "아이디 @ 도메인", 둘째 줄 "도메인 선택"). 이유: 390px에서 3조각을 한 줄에 두니 칸이 약 70px로 좁아져 입력한 글자가 다 보이지 않는다.
- 약관은 "전체 동의" 한 줄 + 항목마다 "체크 · 제목 · (필수)/(선택) · 내용 보기(접힘)"으로 줄인다. 이유: 본문 5개를 펼치니 PC에서 2,000px가 약관이다. 제출 버튼이 양식에서 너무 멀어진다.
- 3열 카테고리 라디오는 쓰지 않고 상품 검색(자동완성 + 결과에서 고르기)으로 바꾼다. 이유: 우리 상품은 이름·품번으로 찾는다.

쓰지 않을 것
- 제목과 양식 사이의 홍보 배너 3개. 이유: 양식을 화면 아래로 밀어낸다(모바일 첫 화면이 배너로 다 찬다).
- 내용을 가리는 떠 있는 바로가기 묶음. 이유: 모바일에서 입력 칸과 제목을 가린다. 우리는 하단 상담 바 하나만 둔다.
- 표마다 반복하는 "* 표시는 필수 입력 항목입니다." 이유: 양식 맨 위 한 번이면 된다.

## 3. 샵다나와 PC견적 — 여러 상품을 한 화면에서 고르고 오른쪽에 요약

- 주소: https://shop.danawa.com/virtualestimate/?controller=estimateMain&methods=index&marketPlaceSeq=16 (모바일은 mshop.danawa.com 으로 넘어간다)
- 본 날짜: 2026-11-17
- 캡처: danawa-estimate-pc.jpg (처음 상태), danawa-added-pc.jpg (CPU와 메모리를 하나씩 담은 상태), danawa-estimate-m.jpg (모바일 처음 상태), danawa-added-m.jpg (모바일에서 하나 담은 뒤), danawa-cart-m.jpg ("PC견적 카트"를 연 화면)
- 모바일 첫 접속 때 앱 설치 안내가 떠서 "모바일 웹으로 볼게요"를 눌러 닫고 찍었다. 위쪽 광고 배너는 닫을 수 없어 그대로 찍혔다.

관찰한 사실
- PC는 2열이다. 왼쪽(약 845px)은 고르는 곳, 오른쪽(약 400px)은 요약("견적카트")이다.
- 왼쪽 순서: 상품명 검색 칸(전체 폭 + 오른쪽 끝 검색 단추) → 지금 품목 이름 + 상품 개수("CPU 상품개수 : 1176개") → 속성 체크 표(제조사, 종류, 규격… 줄마다 체크 5개 + 더 보기) → 정렬 탭 5개(인기상품순·신상품순·낮은 가격순·높은 가격순·상품명순) + "결과 내 검색" → 결과 목록 → 쪽 번호.
- 결과 한 줄: 체크 · 작은 사진 · 상품명(굵게) · 규격 한 줄(넘치면 …) · 표식 → 오른쪽에 가격과 "담기 →" 버튼. 담으면 그 줄에 진한 테두리가 생기고 버튼이 "해제"(채운 버튼)로 바뀐다.
- 오른쪽 요약: 맨 위 탭 2개(현금 최저가 / 카드 최저가) → "견적카트" 표식 + 한 줄 안내("로그인하여 저장한 견적들을 확인해보세요.") → 품목 칸 목록. 품목 칸은 "PC 주요구성"(CPU, 쿨러/튜닝, 메인보드, 메모리…)과 "모니터 및 주변기기" 두 묶음으로 나뉘고 묶음 제목 옆 화살표로 접는다.
- 품목 칸의 세 상태: 빈 칸은 이름만 있는 흰 줄, 지금 고르는 칸은 색을 채운 줄, 담긴 칸은 이름 줄 아래에 "상품명 / − 1 + 수량 / 가격 / ×(삭제)"가 붙는다. 빈 칸을 누르면 왼쪽 목록이 그 품목으로 바뀐다(메모리 칸을 누르니 왼쪽이 "메모리 상품개수 : 1955개"가 됐다).
- 요약 맨 아래: 추가 상품 선택 한 줄 → "총 2개 품목선택" + "전체삭제" → "총 합계금액 1,131,940원" → 버튼 4개(견적신청하기 / 구매하기 / 호환성 체크 / PC구매상담, 2×2) → 요약 밖 아래에 작은 버튼 4개(견적저장 · 견적불러오기 · 견적공유 · 견적캡처).
- 로그인하지 않아도 담기·수량·삭제·합계가 모두 동작했다. 로그인은 요약 머리의 한 줄로만 권한다.
- PC와 모바일 차이: 모바일은 요약이 화면에서 빠진다. 위에 검색 칸 + "PC견적 카트" 버튼이 한 줄에 있고, 본문은 왼쪽 목록(약 82%) + 오른쪽 세로 품목 탭(약 18%, 지금 품목은 색 채움)이다. 줄마다 오른쪽 아래에 장바구니 아이콘 단추가 있고 속성 체크 표는 "상세검색" 버튼 뒤로 들어갔다. 하나 담으면 "PC견적 카트" 버튼과 해당 품목 탭에 숫자 표식(1)이 붙고 그 줄의 아이콘 단추에 색 테두리가 생긴다. 카트는 별도 화면이다: 위에 "← · PC견적 카트 · 캡처 · 공유", "전체(1개)" 체크 + "선택 삭제 / 견적함 저장", 품목 이름 아래 "체크 · 사진 · 상품명 · 가격 · × · − 1 +" 줄, 안내 상자들, 화면 아래 고정 바("최저가 합계 1,487,840원" + "호환성 체크" 알약, 그 아래 반반 버튼 "견적 신청하기 | 구매하기").
- 검색 칸에 글자를 넣었을 때의 제안 목록은 찍지 못했다.

우리가 가져올 것
- PC 2열(왼쪽 넓은 열에서 고르고 적는다, 오른쪽 약 400px 요약에 쌓인다). 이유: 상품이 여러 개여도 지금까지 담은 것과 합계가 항상 보인다.
- 요약 줄 구성(상품명 / 수량 − 1 + / ×)과 맨 아래 "총 n개 품목" + "전체삭제" + 큰 제출 버튼. 이유: 추가·삭제·수량을 요약에서 바로 고친다.
- 결과 줄의 "담기 → 해제" 전환과 담긴 줄 테두리. 이유: 검색 결과 안에서 이미 고른 상품이 보이고, 같은 자리에서 취소된다.
- 모바일에서 요약을 "건수 표식이 붙은 버튼 → 별도 화면(또는 아래에서 올라오는 패널) + 하단 고정 바(요약 한 줄 + 제출 버튼)"로 바꾸는 것. 이유: 390px에서는 2열이 안 된다.
- 로그인 안내를 막는 화면이 아니라 요약 머리의 한 줄로 두는 것. 이유: 비회원도 끝까지 채워 볼 수 있고, 저장·불러오기 같은 회원 기능만 로그인으로 넘긴다.

바꿔서 쓸 것
- 품목 칸(CPU·메모리…)을 "상품 1 · 상품 2 …" 칸으로 바꾼다. 빈 칸은 "상품 추가" 한 줄만 둔다. 이유: 우리는 정해진 품목 틀이 없고 상품 수가 자유다.
- 요약 머리에 "필수 6 / 8 입력"처럼 채운 비율 한 줄을 넣고, 덜 채운 상품 줄에는 "수량 입력 필요" 표식을 붙인다. 이유: 다나와에는 없지만 우리 요구(필수값 채운 비율)이고, GOV.UK 작업 목록의 완료/미완료 표식과 같은 역할이다.
- 가격·합계 자리는 "총 수량 n벌"로 바꾼다. 이유: 견적 전이라 가격을 보여 주지 않는 상품이 있다.
- 버튼은 2×2 네 개 대신 "견적 요청" 하나(`.bt--acc`)와 선 버튼 "임시 저장" 하나로 줄인다. 이유: DESIGN.md가 제출 버튼 하나를 요구한다.

쓰지 않을 것
- 화면 위 광고 띠·기획전 배너, 결과 목록 안 광고 줄. 이유: 우리 양식에는 광고가 없다.
- 속성 체크 표(줄마다 체크 5개 이상). 이유: 견적 양식 안 검색은 이름·품번 검색과 분류 칩 정도면 된다.
- 촘촘한 글자 크기와 줄 간격. 이유: 우리 입력 칸은 높이 48px, 본문 15px 기준이다.

관찰한 사실
- 공통: 본문은 가운데 한 열(PC 약 630px)이고 버튼은 PC에서 왼쪽 정렬, 모바일에서 전체 폭이다.
- 오류 요약: "뒤로" 링크 아래, 제목(h1) 위에 테두리 상자가 온다. 상자 안은 굵은 제목 "There is a problem" + 오류 문장 목록이고 문장마다 해당 칸으로 가는 링크다. 그 아래 질문 묶음 전체 왼쪽에 세로 막대가 생기고, 라벨과 입력 칸 사이에 같은 문장이 굵게 다시 나온다. 날짜 3칸(Day·Month·Year) 가운데 비어 있는 Year 칸만 테두리 색이 바뀌고 Day(5)·Month(12)에 넣은 값은 남아 있다.
- 답 확인: 제목 → 묶음 제목(h2) "Personal details", "Application details" → 묶음마다 줄 목록. PC 한 줄은 3칸이다: 항목 이름(굵게, 약 1/3) · 입력한 값(여러 줄 가능: 주소 3줄, 연락처 2줄) · 오른쪽 끝 "Change" 링크. 줄 사이는 1px 선이다. 비워 둔 선택 항목은 "Not provided"로 적혀 있다. 맨 아래에 "Now send your application" 제목 + 확인 문장 + 제출 버튼("Accept and send").
- 작업 목록: 제목 → 묶음 제목(h2) 2개 → 줄마다 왼쪽에 작업 이름(링크), 오른쪽 끝에 상태. 끝난 것은 글자만("Completed"), 안 끝난 것은 옅은 색 표식("Incomplete")이라 할 일이 더 눈에 띈다. 맨 아래에 버튼 하나("Apply").
- 자동완성: 라벨은 칸 위. "un"을 넣으니 칸 바로 아래에 칸과 같은 폭으로 제안 9줄이 붙어 열린다. 스크롤바 없이 전부 보이고 줄마다 바탕이 번갈아 바뀐다. PC에서 아래 방향키를 누르니 첫 줄이 색으로 강조됐다. 목록은 아래 내용을 밀지 않고 위에 덮인다.
- PC와 모바일 차이: 답 확인의 3칸 줄이 모바일에서는 "이름 / 값 / Change" 세로 3줄로 쌓인다. 작업 목록은 모바일에서도 "이름 왼쪽 · 상태 오른쪽" 한 줄을 유지한다. 오류 요약은 구조가 같고 문장만 줄바꿈된다. 자동완성 제안 줄 높이는 PC·모바일 모두 약 35px이다.

우리가 가져올 것
- 오류를 두 곳에 같이 보이기: 양식 맨 위 요약 상자(오류마다 해당 칸으로 가는 링크) + 해당 칸 위 같은 문장. 이유: 긴 양식에서 틀린 칸이 화면 밖에 있어도 한 번에 찾아간다.
- 묶음 칸(연락처 3칸, 날짜)은 틀린 칸에만 테두리 색을 바꾸고 나머지 칸의 값은 그대로 두는 것. 이유: 다시 다 치게 하지 않는다.
- 답 확인의 "이름 · 값 · 변경" 줄과 "입력 안 함" 표기, 모바일 세로 쌓기. 이유: 한 화면 양식의 오른쪽 요약과 제출 전 확인에 같은 줄 모양을 쓸 수 있다.
- 작업 목록의 "끝난 것은 글자만, 안 끝난 것은 표식" 규칙. 이유: 요약에서 덜 채운 상품·묶음이 먼저 보인다.
- 자동완성 목록을 칸 바로 아래 같은 폭으로, 스크롤바 없이 여는 것과 방향키 강조. 이유: 양식 안 상품 검색에 그대로 쓴다.

바꿔서 쓸 것
- 오류 문장을 칸 위가 아니라 우리 `.fld__help` 자리(칸 아래)에 둔다. 이유: DESIGN.md의 `.fld.is-err` 규칙이 도움말 줄을 오류 색으로 바꾸는 방식이다. 요약 상자는 `.note` 모양에 오류 색 1px 테두리를 더해 만든다.
- 자동완성 줄에 상품 사진(40px)·상품명·품번을 넣고 PC 10줄, 모바일 8줄까지만 보인다. 이유: 예시는 글자 한 줄뿐이고, 줄 수 기준은 Baymard 글을 따른다.
- 작업 목록의 상태 글자를 "입력 완료 / 입력 필요"로 바꿔 요약의 상품 줄 오른쪽에 붙인다.

쓰지 않을 것
- 한 화면에 질문 하나만 두는 흐름 전체. 이유: 우리는 대화형과 한 화면 양식 두 가지를 이미 정했다.
- 왼쪽 정렬 좁은 버튼. 이유: 우리 제출 버튼은 알약이고 모바일 전체 폭이다.

## 5. MOJ Design Patterns "Add another" 예시 — 같은 묶음 추가·삭제

- 주소: https://design-patterns.service.justice.gov.uk/components/add-another/examples/stacked-errors (설명 글: https://design-patterns.service.justice.gov.uk/components/add-another/)
- 본 날짜: 2026-11-17
- 캡처: moj-add-another-pc.jpg, moj-add-another-m.jpg
- 디자인 시스템이 공개한 예시 화면이다(사이트 머리·푸터 없이 양식만 있다).

관찰한 사실
- 묶음마다 제목에 순번과 전체 수가 있다("Participant 1 of 2", "Participant 2 of 2").
- 묶음 안 순서: 이름 칸(전체 폭) → 생년월일(예시 도움말 한 줄 + 좁은 칸 3개) → 묶음 맨 아래 "Remove participant 1" 버튼(약한 버튼, 버튼 글자에 순번 포함) → 가로 선.
- 마지막 묶음 아래에 "Add another participant" 버튼(약한 버튼)이 하나 있다.
- 오류 요약 문장에 몇 번째 묶음인지 들어 있다("Date of birth for participant 1 must include a year"). 그 묶음의 날짜 칸 왼쪽에 세로 막대, 칸 위에 같은 문장, 빈 Year 칸에만 테두리 색.
- PC와 모바일 차이: 구조는 같다. 모바일에서 삭제·추가 버튼이 전체 폭이 된다. PC 예시는 칸이 창 폭 전체로 늘어나 있다(예시라 폭 제한이 없다).
- 설명 글에는 "항목이 제출할 때만 저장되므로 새로 고치면 잃을 수 있다. 칸이 적고 몇 번만 반복할 때 쓰라"고 적혀 있다.

우리가 가져올 것
- 묶음 제목 "상품 1 / 2"(순번 / 전체 수), 묶음 맨 아래 "상품 1 삭제", 마지막 묶음 아래 "상품 추가", 묶음 사이 1px 선. 이유: 한 화면 양식의 상품 추가·삭제를 이 네 가지로 만들 수 있다.
- 오류 문장에 순번을 넣는 것("상품 2의 수량을 입력하세요."). 이유: 같은 칸이 여러 번 나와도 어느 것인지 안다.

바꿔서 쓸 것
- 삭제 버튼을 묶음 제목 줄 오른쪽 끝(글자 버튼 "삭제")으로 올리고, 상품이 하나뿐일 때는 숨긴다. 이유: 상품 블록이 길어 맨 아래까지 내려가야 삭제가 보이면 불편하다. 예시의 묶음은 칸이 2개뿐이다.
- 입력 중인 내용은 브라우저에 임시 저장한다. 이유: 설명 글이 지적한 "새로 고치면 잃는다"를 막는다. 상품 블록은 칸이 많다.

쓰지 않을 것
- 창 폭 전체로 늘어난 입력 칸. 이유: 예시라서 그렇다. 우리는 왼쪽 열 폭 안에 둔다.

## 사용성 근거

Nielsen Norman Group
- "Website Forms Usability: Top 10 Recommendations" (Kathryn Whitenton, 2016) https://www.nngroup.com/articles/web-form-design/
  - 한 열로 쌓는다. 여러 열은 아래로 내려가는 흐름을 끊는다. 다만 시·도/우편번호처럼 짧고 한 덩어리인 칸은 한 줄에 둘 수 있다.
  - 라벨은 칸 가까이, 관련 칸은 묶음으로. 자리 표시 글자(placeholder)를 라벨 대신 쓰지 않는다. 칸 폭은 들어갈 값 길이에 맞춘다.
  - 초기화 버튼을 두지 않는다. 오류는 색 하나에 기대지 않고 테두리·글자 등 여러 신호로 보이고, 입력한 값은 지우지 않는다.
- "Marking Required Fields in Forms" (Raluca Budiu, 2019) https://www.nngroup.com/articles/required-fields/
  - 필수 칸은 전부 표시한다. 양식 위 안내문만으로는 부족하다(사람들은 위 안내를 읽지 않는다). 별표는 익숙한 표시이고, 선택 칸에 "선택"을 붙이면 추측이 줄어든다.
- "10 Design Guidelines for Reporting Errors in Forms" (Rachel Krause, 2019) https://www.nngroup.com/articles/errors-forms-design-guidelines/
  - 오류 문장은 해당 칸 옆에 둔다. 요약만으로 오류를 알리지 않는다. 다 치기 전에 오류를 띄우지 않는다. 오류를 말풍선(툴팁)이나 팝업으로 알리지 않는다.
- "Wizards: Definition and Design Recommendations" (Raluca Budiu, 2017) https://www.nngroup.com/articles/wizards/
  - 단계 목록을 보여 주고 지금 단계를 강조한다. 단계 이름은 내용을 적는다("다음" 대신 다음에 할 일). 이전으로 돌아가는 버튼을 둔다. 중간에 나갔다가 이어서 할 수 있게 저장한다.

Baymard Institute
- "Form Field Usability: Avoid Extensive Multicolumn Layouts" (2023) https://baymard.com/blog/avoid-multi-column-forms
  - 여러 열 양식은 칸을 건너뛰거나 잘못 읽게 만든다(조사한 사이트의 16%가 이 실수). 한 줄에 2~3칸을 두는 것은 날짜·이름·우편번호처럼 한 덩어리일 때만, 나머지가 한 열일 때만 괜찮다.
- "Usability Testing of Inline Form Validation" (2024) https://baymard.com/blog/inline-form-validation
  - 조사한 사이트의 31%에 칸 단위 검사가 없다. 검사는 칸을 떠날 때 한다(치는 중에는 하지 않는다). 고치면 그 즉시(글자 단위로) 오류를 지운다. 맞게 넣은 칸에 확인 표시를 주면 다시 훑어보는 일이 준다.
- "9 UX Best Practice Design Patterns for Autocomplete Suggestions" (2022) https://baymard.com/blog/autocomplete-design
  - 제안은 PC 10개 이하, 모바일 4~8개. 목록 안 스크롤바를 두지 않는다. 사용자가 친 부분이 아니라 이어지는 부분을 강조한다. 방향키 이동과 고른 줄 강조를 지원한다.

GOV.UK Design System / MOJ Design Patterns
- Question pages https://design-system.service.gov.uk/patterns/question-pages/
  - 한 화면에 질문 하나로 시작한다. 위에 "뒤로" 링크를 둔다. 진행 표시는 먼저 없이 시험해 보고, 필요하면 "질문 3 / 9"처럼 단순하게 쓴다. 모든 단계를 늘어놓는 표시는 잘 눈에 띄지 않고 작은 화면에서 자리를 많이 쓴다(12단계 표시를 없애도 완료율이 그대로였다는 사례를 든다).
- Error summary https://design-system.service.gov.uk/components/error-summary/
  - 오류가 하나여도 요약을 보인다. 요약은 본문 맨 위, 제목 위에 둔다. 요약 문장과 칸 옆 문장을 똑같이 쓴다. 문장은 해당 칸으로(묶음 칸은 틀린 첫 칸으로) 연결하고, 요약으로 초점을 옮긴다.
- Check answers https://design-system.service.gov.uk/patterns/check-answers/
  - 제출 전에 답을 묶음 제목 아래 모아 보여 주고 항목마다 "변경" 링크를 둔다. 고친 뒤에는 확인 화면으로 바로 돌아온다. 건너뛴 선택 항목은 "입력 안 함"으로 적는다. 버튼 글자는 하는 일을 적는다.
- Complete multiple tasks https://design-system.service.gov.uk/patterns/complete-multiple-tasks/
  - 상태는 "완료 / 미완료" 두 가지로 시작한다. 완료는 바탕 없는 글자, 할 일이 남은 것만 표식으로 띄운다. 빨강은 오류에만 쓴다.
- MOJ Add another https://design-patterns.service.justice.gov.uk/components/add-another/
  - 칸이 적고 몇 번만 반복할 때 쓴다. 제출할 때만 저장되므로 길고 복잡한 묶음에는 맞지 않는다. 오류는 묶음 하나씩 요약에 보인다.

DESIGN.md와 부딪히는 점 한 가지
- DESIGN.md "견적문의" 조립법은 `.fld` 폼을 2열(폰 1열)로 적어 두었다. 위 두 글(NN/g, Baymard)은 한 열을 권하고 한 덩어리인 짧은 칸만 한 줄에 두라고 한다. LG도 PC는 한 줄에 항목 하나다. 2열을 "연락처 3칸, 이메일 아이디·도메인, 우편번호·주소찾기처럼 한 덩어리인 칸만 나란히"로 좁혀 쓰는 쪽을 권한다. 결정은 디자인 쪽 몫이다.

## 이 유형에 그대로 쓸 수 있는 문장

1. 대화형 입력은 질문 카드를 하나만 열어 두고, 답한 질문은 위에 "질문(왼쪽) → 내 답(오른쪽) → 답 아래 '수정' 링크" 묶음으로 쌓는다. 화면 맨 위에는 양식 이름과 진행률 막대를 고정하고 막대 오른쪽에 "3 / 8 · 38%"를 적는다.
2. 질문 카드의 "다음" 버튼은 카드 맨 아래 전체 폭에 두고 답을 고르기 전에는 비활성이다. 선택 질문에만 "다음" 왼쪽에 "건너뛰기" 선 버튼을 붙이고, 건너뛴 질문에도 "건너뛰었습니다." 답 줄과 "수정"을 남긴다.
3. 이전 답의 "수정"을 누르면 그 질문이 제자리에서 카드로 다시 열리고 전에 고른 값이 선택돼 있다. 링크는 "수정 취소"로 바뀌고, 뒤에 답한 내용과 진행률은 그대로 둔다.
4. 사이즈별 수량은 "사이즈 이름(왼쪽) + − 숫자 +(오른쪽)" 줄을 사이즈 수만큼 세로로 쌓는다. 숫자 칸은 직접 입력할 수 있고, 합계가 1 이상일 때만 "다음"이 켜진다. 답 줄에는 0이 아닌 사이즈만 "· M 30 · L 20"으로 적는다.
5. 한 화면 입력 양식은 PC에서 2열이다. 왼쪽 넓은 열에 상품 블록과 입력 칸, 오른쪽 약 400px 열에 요약을 둔다. 요약 순서는 "필수 6 / 8 입력" 한 줄 → 상품별 한 줄(상품명 · 수량 · 삭제 ×, 덜 채운 줄에만 "입력 필요" 표식) → "총 n개 상품 · 전체 삭제" → "견적 요청" 버튼이다.
6. 모바일에서는 요약을 화면에서 빼고, 위에 건수 표식이 붙은 "요약 보기" 버튼, 아래에 고정 바(요약 한 줄 + "견적 요청" 버튼)를 둔다. "요약 보기"는 상품별 줄과 삭제·수량 조절이 있는 전체 화면 패널을 연다.
7. 상품 블록은 제목을 "상품 1 / 2"(순번 / 전체 수)로 쓰고 제목 줄 오른쪽에 "삭제"를 둔다(상품이 하나면 숨김). 블록 사이는 1px 선으로 나누고 마지막 블록 아래에 "상품 추가" 버튼을 하나 둔다.
8. 양식 안 상품 검색은 입력 칸 바로 아래에 칸과 같은 폭으로 제안 목록을 붙인다(PC 10줄, 모바일 8줄까지, 목록 안 스크롤바 없음, 방향키로 고른 줄 강조). 결과 줄은 "사진 · 상품명 · 품번 한 줄 + 오른쪽 '담기'"이고, 담은 줄은 테두리를 진하게 하고 버튼을 "해제"로 바꾼다.
9. 오류는 두 곳에 같은 문장으로 보인다. 양식 맨 위 요약 상자(제목 + 오류마다 해당 칸으로 가는 링크, 상품이 여러 개면 "상품 2의 수량을 입력하세요."처럼 순번을 넣는다)와 해당 칸 아래 도움말 줄이다. 연락처 3칸·날짜 같은 묶음 칸은 틀린 칸에만 테두리 색을 바꾸고 나머지 칸의 값은 지우지 않는다. 검사는 칸을 떠날 때 하고, 고치는 즉시 오류를 지운다.
10. 긴 양식은 한 열로 쌓고 묶음마다 제목을 단다(문의 상품 → 담당자 정보 → 납품 정보 → 첨부 파일 → 동의 → 버튼). 한 줄에 나란히 두는 것은 한 덩어리인 칸뿐이다: 연락처 "국번 선택 − 4자리 − 4자리", 이메일 "아이디 @ 도메인"(도메인 선택은 PC에서 같은 줄, 모바일에서 다음 줄), "우편번호 + 주소찾기 버튼". 필수 칸은 모두 라벨 뒤에 *, 선택 칸은 "(선택)"을 붙이고, 동의는 "전체 동의" 한 줄 아래 항목마다 "체크 · 제목 · (필수)/(선택) · 내용 보기(접힘)"으로 둔다.
