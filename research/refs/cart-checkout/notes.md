## 3. 남긴 곳

### 3-1. AS Colour

- 주소: https://www.ascolour.com/ (경로 미확인. 상품은 "Made Hood 5151", 화면은 그 상품의 Bulk Order Grid 와 Cart)
- 본 날짜: 2026-11-17
- 캡처: `ascolour-bulk-grid-pc.jpg`, `ascolour-bulk-grid-m.jpg`, `ascolour-cart-pc.jpg`, `ascolour-cart-m.jpg`

관찰한 사실 — 수량 표(Bulk Order Grid)

- PC 정보 순서: 상품명과 품번(왼쪽) · "Back to Product" 링크(오른쪽) → 색상 검색칸 + "clear search" → 수량 표 → 사이즈별 합계 행(TOTALS) → 설명문(왼쪽) + "Total Quantity: 33" + "Add to Cart" 버튼(오른쪽).
- 표는 7열이다. 1열은 색상(견본 원 + 색상 이름), 2~7열은 사이즈 6개(SML, MED, LRG, XLG, 2XL, 3XL)다. 색상 하나가 창고 2곳(CARSON, CA / CHARLOTTE, NC)의 2행으로 나뉜다.
- 칸 하나가 입력칸 하나다. 비어 있는 칸에는 자리 표시로 재고 수("224 AVAIL.")나 입고 예정일("ETA 06 Feb")이 적혀 있다. 수량을 넣은 칸은 칸 전체가 채워진 칸으로 바뀌어 빈 칸과 구분된다.
- 맨 아래 TOTALS 행이 사이즈별 합을 보여 준다(15 / 8 / 0 / 0 / 0 / 10). 그 아래 총 수량 33이 버튼 바로 왼쪽에 있다.
- 한 화면(1440×900)에 색상 3개 × 사이즈 6개 × 창고 2곳이 스크롤 없이 들어 있다.
- 모바일은 표를 그대로 줄이지 않는다. 위에서 색상 견본 줄로 색상 하나를 고르고("Selected Colour: Athletic Heather"), 아래에 창고별 블록이 세로로 쌓인다. 블록 하나는 "COLOR: ATHLETIC HEATHER" 머리줄 + 사이즈 3칸 × 2줄이다. 사이즈 이름 칸 바로 아래에 입력칸이 있고, 입력칸에는 PC와 같은 재고 자리 표시가 있다. "Add to Cart" 버튼은 블록 아래에 화면 폭 전체로 있다. TOTALS 행은 모바일 캡처에 보이지 않는다.

관찰한 사실 — 장바구니

- PC는 2열이다. 왼쪽 목록이 약 56%, 오른쪽 요약이 약 40%를 차지한다.
- 제목이 "Your Cart (33)"이다. 괄호 안 숫자는 상품 종류 수가 아니라 총 수량이다.
- 목록은 3단으로 묶인다. 상품("Made Hood | 5151") → 색상(상품 사진 + 색상 이름) → 사이즈 행. 사이즈 행 한 줄에 사이즈, 단가(할인가와 정가), "Remove" 글자 링크, "− 수량 +" 조작이 순서대로 있다.
- 수량 표에서 창고 2곳에 나눠 넣은 SML 5개와 10개가 장바구니에서는 SML 15 한 줄로 합쳐져 있다.
- 목록 끝에 "CLEAR CART ×"가 있다.
- 오른쪽 열 순서: 부가 선택(Carbon Offset) 상자 → Gift Voucher(접혀 있음, "Show") → Subtotal → Shipping "Calculated at Checkout" → Total → "Checkout" 버튼(열 폭 전체).
- 모바일은 1열이다. 3단 묶음을 그대로 유지하고, 사이즈 행도 한 줄(사이즈·단가 / Remove / − 수량 +)을 유지한다. 요약과 Checkout 버튼은 목록 아래에 온다. 화면 아래에 고정된 버튼은 캡처에 없다.
- 단계: 상품 화면(수량 표) → 장바구니 → Checkout. Checkout 이후 화면은 찍지 않았다.

가져올 것

- 장바구니 목록을 "상품 → 색상 → 사이즈 행" 3단으로 묶는다. 같은 상품을 색상·사이즈마다 따로 담긴 줄로 흩어 놓지 않아야 구매 담당자가 "이 상품을 몇 벌 요청하는지"를 한 덩어리로 본다.
- 사이즈 행 한 줄에 "사이즈 · − 수량 + · 삭제"를 둔다. 단체복은 사이즈 하나의 수량만 고치는 일이 잦으므로 창을 열지 않고 행에서 바로 고친다.
- 제목 옆에 총 수량을 적는다("장바구니 (120벌)"). 단체 주문은 종류 수보다 총 수량이 확인 대상이다.
- 수량 표 아래에 사이즈별 합계 행과 총 수량을 둔다. 인원 명단의 사이즈별 인원과 대조할 수 있다.
- 모바일에서는 표를 통째로 줄이지 않고, 색상 하나를 먼저 고른 뒤 사이즈를 3칸씩 줄바꿈한다.

바꿔서 쓸 것

- 창고 2행은 쓰지 않고 색상 1행 = 1줄로 한다. 우리는 창고를 구매자가 고르지 않는다.
- 자리 표시의 재고 수는, 재고를 보여 줄 수 있는 상품에만 쓴다. 맞춤 작업복처럼 재고 개념이 없는 상품은 빈 칸에 "0"만 둔다.
- 단가 자리: 가격이 있는 상품은 단가를, "견적문의" 상품은 숫자 대신 "견적 후 안내"를 적는다.
- 색상 묶음 머리줄 아래에 "인쇄: 있음(왼쪽 가슴, 자수) · 포장: 개별 포장"처럼 인쇄·포장 요약 한 줄과 "변경" 링크를 더한다. AS Colour 에는 이 항목이 없다.
- 요약의 Shipping "Calculated at Checkout" 자리는 "배송비·인쇄비는 견적서에서 안내합니다."로 바꾼다.
- 모바일 수량 표에도 사이즈별 합계와 총 수량을 버튼 위에 둔다(AS Colour 모바일에는 보이지 않았다).

쓰지 않을 것

- 요약 위의 부가 판매 상자(Carbon Offset). 합계와 버튼을 아래로 밀어낸다.
- 목록 바로 아래의 "장바구니 전체 비우기". 우리는 선택 삭제가 있으므로 실수로 전부 지울 수 있는 버튼을 따로 두지 않는다.
- 장바구니를 배경 위에 뜬 창처럼 띄우는 구성. 우리는 일반 페이지로 만든다.

### 3-2. SSF SHOP

- 주소: https://www.ssfshop.com/ (경로 미확인. 화면은 장바구니와 "옵션/수량 변경" 창)
- 본 날짜: 2026-11-17
- 캡처: `ssf-cart-pc.jpg`, `ssf-cart-m.jpg`, `ssf-cart-option-pc.jpg`, `ssf-cart-option-m.jpg`

관찰한 사실 — 장바구니

- PC 정보 순서: 제목 "장바구니"(가운데) → 배송 유형 탭 4개(일반배송 (1) / 빠른배송 (0) / 매장픽업 (0) / 예약주문 (0), 각 탭에 개수) → 목록 머리줄 → 상품 행 → 이용안내.
- PC는 2열이다. 왼쪽 목록이 약 65%, 오른쪽 "결제정보" 상자가 약 28%다.
- 목록 머리줄 한 줄에 "전체 선택" 체크박스, "선택 삭제" 글자 버튼이 왼쪽에, "품절상품 삭제" 버튼(해당 없을 때 비활성)이 오른쪽에 있다.
- 상품 행: 체크박스 → 상품 사진 → 브랜드 · 상품명(한 줄로 자르고 "…") · "옵션 남색, 036, 1개" · 정가(취소선) · 할인율과 판매가 → 버튼 2개("옵션/수량 변경", "바로구매")가 세로로 → 오른쪽 위 X(삭제).
- 상품 행 아래에 배송 안내 띠("무료배송 | 입점 파트너에서 출고예정")가 있고, 그 아래 상품별 금액 상자(상품가격 / 배송비 + 조건 설명 / 할인내역(펼침 화살표) / 예상 결제 금액)가 있다.
- 오른쪽 "결제정보" 상자 순서: 상품금액 → 배송비 → 할인금액(안쪽 작은 상자에 상품할인·즉시할인 내역) → 구분선 → 총 구매 금액 → "1건 주문하기" 버튼. 버튼 글자에 선택한 건수가 들어 있다.
- 목록 아래 "이용안내"는 글머리표 4줄이다(보관 개수·기간, 배송비 기준, 합배송 기준 등).
- 모바일: 위 띠가 "뒤로 화살표 + 장바구니 + 홈·검색·장바구니 아이콘"으로 바뀐다. 탭 4개는 한 줄에 그대로 있다. 상품 행은 체크박스 + 작은 사진 + 글자, 그 아래 버튼 2개가 가로로 나란히(각 절반 폭), 그 아래 금액 상자 순서다.
- 모바일에는 화면 아래에 "총 구매금액 159,200원" + "1건 구매하기"(화면 폭 전체) 띠가 있다. 전체 캡처에서 첫 화면 높이의 아래쪽에 겹쳐 찍혀 있어 화면 아래 고정 띠로 보인다. PC의 "결제정보" 상자 내역(상품금액·배송비·할인)은 모바일 띠에 없고 총액만 있다.

관찰한 사실 — 옵션/수량 변경 창

- 모바일은 1열이고 상품 사진을 글자 위에 크게 쌓는다. 상품 2개와 요약에 그림 세로 4200px(화면 약 2.5개 분량)을 쓴다. 맨 아래 "결제" 버튼은 화면 폭 전체다.

관찰한 사실 — 결제 첫 단계(받는 방법)

- 위 띠: 왼쪽 "결제", 오른쪽 "주문 요약 정보 표시: ₩214,000"(모바일은 "₩214,000"만). 요약은 접혀 있고 링크로 연다.
- 화면 제목이 질문이다: "주문하신 제품을 어떻게 받으시겠습니까?"
- 그 아래 큰 선택 버튼 2개가 나란히 있다("배송을 원합니다" / "직접 픽업하겠습니다", 각각 아이콘 + 글자). 고른 쪽만 테두리로 구분된다. 그 아래 "배송지: 04524"(우편번호, 누르면 바꿈).
- 상품이 받는 시점별 묶음으로 나뉜다. 묶음 제목이 문장이다: "재고가 있으며, 배송 준비가 끝났습니다." / "2-3주 후 배송." / "제품을 함께 일괄 배송." 각 묶음에 해당 상품의 작은 사진과 이름이 있다.
- 묶음마다 "배송 방법:" 아래 카드형 선택지가 있다. 카드 왼쪽에 "도착 예정 익일"과 설명("표준 배송(오전 8시~오후 8시)"), 오른쪽에 요금("무료")이 있다. 고른 카드만 테두리로 구분된다.
- 화면 아래 "유의해야 할 점:" 글머리표 3줄과 자세히 보기 링크가 있다.
- 한 화면에 질문 하나만 있다. 주소·결제수단 입력은 다음 단계다(찍지 않았다. 개인정보 입력이 필요하다).
- 모바일은 PC와 순서가 같다. 선택 버튼 2개는 한 줄에 나란히 유지되고, 카드형 선택지는 화면 폭 전체다.

가져올 것

- 배송방법 4종을 카드형 선택지로 둔다. 카드 왼쪽에 이름과 조건 설명, 오른쪽에 요금을 적는다("택배 / 2~3일 / 3,000원", "화물 / 대량 주문 / 착불", "퀵 / 당일 / 착불", "방문 수령 / 무료"처럼 실제 값으로).
- 배송지 지정 방식 3종을 큰 선택 버튼으로 먼저 묻고, 고른 방식에 따라 아래 입력 구역이 바뀌게 한다.
- 묶음 제목을 상태 문장으로 쓴다("재고가 있으며, 배송 준비가 끝났습니다."). 우리 완료 화면·주문 내역의 "시안 확인 중입니다.", "제작에 들어갔습니다."에 쓴다.
- 장바구니 맨 위에 합계 한 줄과 주 버튼을 두고, 목록 아래 요약 뒤에 같은 버튼을 한 번 더 둔다(모바일에서 고정 띠를 쓰지 않는 화면에 한함).
- 결제 화면 위 띠 오른쪽의 접힌 요약 링크("주문 요약 정보 표시: 금액"). 모바일 주문서 맨 위에 쓴다.
- 선택지 아래 "유의해야 할 점" 글머리표. 배송방법 아래에 "화물·퀵 배송비는 착불입니다."처럼 조건을 적는다.

바꿔서 쓸 것

- 장바구니 제목의 합계 → 우리는 금액이 견적 전일 수 있으므로 "요청 상품 3개 · 총 120벌"로 쓴다.
- 받는 방법 2택 버튼 → 배송지 지정 방식 3택 버튼(PC 한 줄 3칸, 모바일 세로 3줄).
- 도착 예정일 카드 → 희망배송일은 날짜 입력칸 1개 + 설명 한 줄("제작 기간이 있어 가장 빠른 날짜는 2026-12-08입니다."처럼 기준 날짜 포함)로 한다.
- 수량 드롭다운 → 우리는 수량이 수십~수백이므로 숫자 입력칸 + − / + 로 한다.

쓰지 않을 것

- 한 화면에 질문 하나씩 여러 단계로 나누는 흐름. 우리 주문서는 한 화면이다.
- 모바일에서 상품 사진을 화면 폭 가까이 크게 쌓는 배치. 우리는 상품마다 색상·사이즈 행이 여러 줄이라 사진은 작은 썸네일로 둔다.
- 선택(체크박스) 없는 장바구니. 우리는 선택 접수가 있다.
- 상품 행마다 붙는 픽업 안내. 해당 없음.

### 3-5. GOV.UK Design System (패턴 예시 화면)

- 주소(실제로 연 주소)
  - 완료: https://design-system.service.gov.uk/patterns/confirmation-pages/default/index.html
  - 제출 전 확인: https://design-system.service.gov.uk/patterns/check-answers/default/index.html
  - 오류 안내: https://design-system.service.gov.uk/components/error-summary/full-page-example/index.html
- 본 날짜: 2026-11-17
- 캡처: `govuk-confirmation-pc.jpg`, `govuk-confirmation-m.jpg`, `govuk-check-answers-pc.jpg`, `govuk-check-answers-m.jpg`, `govuk-error-summary-pc.jpg`, `govuk-error-summary-m.jpg`

관찰한 사실 — 완료 화면

- 순서: 완료 상자(큰 글자 "Application complete" + "Your reference number" + 번호 "HDJ2123F") → 한 줄 문장("We have sent you a confirmation email.") → 소제목 "What happens next" → 문단 2개(신청서를 어디로 보냈는지, 그쪽에서 확인 연락을 하거나 추가 정보를 요청한다는 것) → 링크 1개(서비스 의견, 걸리는 시간 "takes 30 seconds" 표기).
- 버튼이 없다. 사진·그림도 없다.
- PC는 한 열이고 본문 폭이 화면 가운데 영역의 약 2/3다. 모바일은 화면 폭 전체이고 순서는 같다. 모바일 한 화면(높이 844px) 안에 완료 상자부터 링크까지 다 들어온다.

관찰한 사실 — 제출 전 확인 화면

- 순서: "Back" 링크 → 제목 "Check your answers before sending your application" → 구역 제목("Personal details", "Application details") → 구역마다 요약 목록 → 소제목 "Now send your application" + 확인 문장 → 버튼 "Accept and send".
- 요약 목록 한 행은 3칸이다: 항목 이름(굵게) | 값 | "Change" 링크(오른쪽 끝). 행 사이는 가는 선으로 나뉜다.
- 값이 여러 줄이면(주소, 연락처) 한 칸 안에서 줄바꿈한다. 입력하지 않은 선택 항목은 "Not provided"로 적혀 있다.
- 입력칸이 하나도 없다. 값은 글자로만 보인다.
- 모바일은 한 행이 세로 3줄로 바뀐다: 항목 이름 → 값 → "Change" 링크. 행 사이 선은 유지된다.

관찰한 사실 — 오류 안내 화면

- 순서: "Back" 링크 → 오류 요약 상자(제목 "There is a problem" + 오류 문장 링크 "Passport issue date must include a year") → 질문 제목 → 같은 오류 문장(입력칸 바로 위) → 입력칸 3개(Day, Month, Year) → 버튼 "Continue".
- 오류 요약 상자는 화면 제목보다 위에 있다. 상자 안 문장은 링크다.
- 같은 문장이 두 군데에 있다: 요약 상자 안, 그리고 입력칸 바로 위.
- 오류가 난 질문 묶음 전체의 왼쪽에 세로 띠가 붙는다. 입력칸 3개 중 비어 있는 Year 칸만 테두리가 다르고, 값이 있는 Day(5)·Month(12) 칸은 그대로이며 입력값이 남아 있다.
- 문장이 무엇이 빠졌는지를 말한다("…must include a year").
- 모바일은 순서가 같고 버튼이 화면 폭 전체다.

가져올 것

- 요청 접수 완료 화면 순서: 완료 문구 + 요청 번호 상자 → "확인 메일을 보냈습니다." 한 줄 → "다음 순서" → 버튼. 모바일 첫 화면 안에 번호와 다음 순서의 첫 줄이 들어오게 한다.
- "다음에 일어나는 일"을 완료 화면에 적는다. 견적 요청은 접수 뒤 과정이 길어서(담당자 확인 → 견적서·시안 → 확정 → 결제 → 제작) 구매 담당자가 다음에 무엇을 기다리는지 적어야 한다.
- 오류는 두 군데에 같은 문장으로 보여 준다: 화면 위 요약 상자(오류마다 해당 칸으로 가는 링크) + 칸 바로 위. 오류가 난 칸만 구분하고 이미 넣은 값은 지우지 않는다.
- 오류 문장은 "무엇을 어떻게 고칠지"로 쓴다("희망배송일을 선택하세요.", "사업자등록번호 10자리를 입력하세요.").
- 수정 불가 구역은 입력칸을 비활성으로 흐리게 두지 않고 "항목 이름 | 값" 요약 목록으로 바꿔 보여 준다. 모바일에서는 이름 → 값 세로 2줄로 쌓는다.
- 입력하지 않은 선택 항목은 빈칸으로 두지 않고 "입력 안 함"으로 적는다.
- 제출 버튼 글자를 행동으로 쓴다("Accept and send" → "견적·시안 요청 접수", "잔금 결제").

바꿔서 쓸 것

- "What happens next" 문단 2개 → 번호 목록 3~4줄로 쓰고 기준 시간을 적는다("1. 담당자가 요청 내용을 확인합니다(영업일 기준 1일 이내). 2. 견적서와 시안을 이메일로 보냅니다. 3. 확정하시면 주문서 작성 링크를 보냅니다."). 시간은 실제 운영 값으로만 적는다.
- 완료 화면에 버튼 2개를 더한다("요청 내역 보기", "쇼핑 계속하기"). GOV.UK 예시에는 버튼이 없다.
- 결제 주문 완료 화면은 같은 순서에 요약 목록을 더한다: 주문 번호 → 결제수단·결제 금액 → (무통장이면) 입금 계좌·입금 기한 → 배송지·배송방법·희망배송일 → 증빙서류.
- 요약 목록의 "Change" 링크 자리 → 잔금 결제 화면에서는 링크를 빼고, 구역 제목 옆에 사유 한 줄("계약 시 확정한 내용이라 변경할 수 없습니다. 변경은 담당자에게 문의하세요.")을 적는다. 고칠 수 있는 구역(결제수단, 증빙서류)만 입력칸으로 둔다.
- 오류 요약 상자 → 우리는 주문서가 한 화면이라 오류가 여러 개 나온다. 상자 제목에 개수를 적고("입력을 확인해 주세요 (3개)") 구역 순서대로 나열한다.

쓰지 않을 것

- 한 화면에 질문 하나만 두는 방식. 우리 주문서는 한 화면이다.
- 제출 전 확인 화면을 별도 단계로 두는 것. 우리는 주문서 오른쪽(모바일은 위)의 요약이 그 역할을 한다. 단계를 하나 더 늘리지 않는다.
- 서비스 의견 설문 링크.

- PC는 2열(목록 약 71%, 요약 약 25%)이다. 제목 "Your cart" 옆에 "1 item".
- 상품 행: 사진 → 공급사 · 상품명 · 규격 → 금액(오른쪽) → 조작 줄("− 1 +", "Remove", "Add note", "Save for later", 수량 할인 표시 "Volume"). 목록 끝에 "Total: 1 items $3.80".
- 요약 상자 순서: 수량 구간 안내("Add 9 more of … to reach the 10+ price break and save 5% per case.") → Subtotal (excl. shipping and taxes) → Shipping → Taxes → Total → 접힌 "Enter Promotion Code" → 버튼 4개가 세로로: "Log in to Checkout"(주 버튼) → "Request Quote" → "Export Cart (.csv)" → "Empty Cart".
- 견적 요청 버튼은 결제 버튼 바로 아래 두 번째 버튼이다. 같은 장바구니에서 결제와 견적 요청 두 길이 갈린다.
- 모바일은 1열(목록 → 요약 → 버튼 4개, 모두 화면 폭 전체). 상품 행의 조작이 세로 4줄로 쌓인다(수량과 Remove / Add note / Save for later / Volume).

관찰한 사실 — 옵션별 수량 표(상품 화면)

- 표 열: SKU | VARIANT | STOCK | QTY("− 12 +") | LINE TOTAL. 열 제목에 정렬 화살표가 있다.
- 표 아래 요약 줄: LINES 1 / UNITS 12 / SUBTOTAL $576.00 + 버튼 "Add 1 line to cart". 버튼 글자에 담기는 줄 수가 들어 있다. 수량을 넣기 전(모바일 캡처)에는 버튼이 "Choose product variant(s) above"로 바뀌고 비활성이다.
- 그 아래 수량별 단가 표(1+ / 10+ / 25+ / 100+, 단가, 할인율). 지금 수량이 속한 구간 행이 구분되어 있다.
- 모바일에서는 표가 화면 폭을 넘어 STOCK 열 중간에서 잘린다. QTY 열이 첫 화면에 보이지 않는다.

쓸 것: (1) 요약 상자에서 요청 버튼과 다른 버튼을 세로로 쌓고 주 버튼을 맨 위에 두는 순서 → 우리는 "견적·시안 요청"이 주 버튼이고 그 아래 "견적서 내려받기(엑셀)" 같은 보조 버튼을 둔다(기능이 있을 때만). (2) 상품 행의 "Add note" → 상품별 요청사항 한 줄 입력. (3) 표 아래 "줄 수 / 총 수량 / 소계" 요약 줄과, 수량을 넣기 전 비활성 버튼의 안내 글자("사이즈별 수량을 입력하세요"). (4) 수량별 단가 표에서 현재 구간 행을 구분하는 것.
쓰지 않을 것: 모바일에서 표를 가로로 넘치게 두는 것(수량 칸이 화면 밖으로 나간다 → 3-1의 사이즈 3칸 줄바꿈을 쓴다). "Empty Cart" 버튼을 요청 버튼과 같은 묶음에 두는 것. 장바구니 위의 로그인 권유 띠.

## 5. 채우지 못한 것

- 상품 정보 자세히 보기(인쇄 방법·부위·첨부파일): 장바구니에서 인쇄 사양과 첨부파일을 보여 주는 화면을 찍지 못했다. 맞춤 인쇄 상점의 장바구니는 대부분 시안 편집기를 거쳐야 상품이 담겨서 로그인·양식 제출 없이 닿을 수 없었다.
- 처리 중 화면(카드 결제 처리): 결제를 실제로 진행해야 나오므로 찍지 못했다. 5장의 NN/g 글만 근거로 둔다.
- 결제 주문 완료 화면: 실제 주문이 필요해 찍지 못했다. 접수 완료 패턴(3-5)을 넓혀 쓴다.
- 잔금 결제의 수정 불가 주문서: 같은 상황의 실제 화면은 없다. 값만 보이는 요약 목록(3-5)으로 대신한다.
- 세금계산서·후불·포인트·희망배송일이 들어간 한글 주문서: 찍지 못했다. 비회원으로 열리는 주문서(3-3)에는 이 항목이 없었다.
- 견적 요청형 장바구니의 실제 영업 사이트 화면: 데모 상점(4-2)만 있다.
- 앞 담당자가 찍은 화면의 정확한 주소: `_capture.py` 가 남아 있지 않아 확인하지 못했다.

## 6. 사용성 근거

아래는 2026-11-17에 해당 글을 열어 확인한 내용이다. 글을 요약 도구로 읽었으므로 수치를 밖에 인용할 때는 원문에서 한 번 더 확인한다.

- Baymard, "Checkout Optimization: 5 Ways to Minimize Form Fields in Checkout"(2024-06-26) — https://baymard.com/blog/checkout-flow-average-form-fields
  결제 과정의 평균 입력칸은 2024년 11.3개이고, 대부분의 사이트는 8개면 된다고 한다. 결제 과정이 길거나 복잡해서 이탈한 경험이 있는 사람이 17%다. 줄이는 방법으로 이름을 한 칸으로, 주소 둘째 줄과 쿠폰 칸을 링크 뒤로 접기, 청구지를 배송지와 같게 기본 설정하기를 든다. 단계 수(평균 5.1)보다 다뤄야 하는 칸 수가 더 중요하다고 한다.
  → 우리: 휴대전화를 한 칸으로, 포인트·요청사항은 접어 두기, "주문자 정보와 같음"을 배송지 지정 방식의 기본값으로.
- Baymard, "Cart Abandonment Rate Statistics" — https://baymard.com/lists/cart-abandonment-rate
  이탈 이유(둘러보기만 한 경우 제외): 추가 비용이 높음 40%, 결제 과정이 길거나 복잡함 17%, 총 금액을 미리 볼 수 없음 12%, 결제수단 부족 9% 등.
  → 우리: 정해지지 않은 금액(인쇄비·배송비)은 숨기지 않고 "견적서에서 안내합니다"로 요약에 적는다.
- Baymard, "Payment UX: Research-Backed Standards for Ecommerce Checkouts" — https://baymard.com/blog/payment-ux
  주문 요약을 결제 단계에서 계속 보이게 하거나 한 번 눌러 열 수 있게 한다(모바일은 접힌 요약). 결제 정보 입력칸보다 앞에 최종 합계를 보여 준다. 쿠폰 칸은 접어 둔다. 가장 많이 쓰는 결제수단을 미리 선택해 둔다. 오류가 나도 입력값을 지우지 않는다(지우는 사이트가 34%). 오류 문장은 구체적으로 쓰고, 문제 칸으로 스크롤하거나 오류가 여럿이면 요약을 보여 준다. 버튼 글자는 다음 행동을 구체적으로 쓴다.
  → 우리: PC 주문서 오른쪽 요약 고정, 모바일 맨 위 접힌 요약, 결제수단 기본 선택, 버튼 글자 "1,040,000원 결제하기".
- Baymard, "Always Collapse Completed Accordion Checkout Steps into Summaries"(2023-09-27) — https://baymard.com/blog/accordion-checkout-usability
  접이식 결제에서 지나간 단계는 제목만 남기지 말고 입력한 값의 요약으로 접는다. 사용자는 앞 단계의 요약을 훑어 입력을 확인한다.
  → 우리: 주문서의 "주문상품" 구역을 접을 때 "3개 상품 · 총 120벌 · 1,040,000원"처럼 요약을 남긴다.
- NN/g, "10 Design Guidelines for Reporting Errors in Forms"(Rachel Krause, 2019-02-03) — https://www.nngroup.com/articles/errors-forms-design-guidelines/
  칸을 떠날 때 바로 검사한다. 입력이 끝나기 전에는 오류를 띄우지 않는다. 오류 문장은 해당 칸 옆에 둔다. 색만 쓰지 않고 아이콘을 함께 쓴다. 위쪽 오류 요약만으로 알리지 않고 칸에도 표시한다. 오류를 툴팁에 숨기지 않는다. 팝업 창은 아껴 쓴다.
- NN/g, "Progress Indicators Make a Slow System Less Insufferable"(Katie Sherwin, 2014-10-26) — https://www.nngroup.com/articles/progress-indicators/
  누르면 즉시 반응을 보여 준다. 약 1초가 넘는 작업에는 진행 표시를 쓴다. 반복 애니메이션은 약 2~10초 작업에, 10초 이상은 진행률 표시를 쓴다. 표시 옆에 무엇을 하는 중인지 글자로 적는다. "다시 누르지 마세요" 경고 대신 첫 누름이 접수됐음을 보여 준다.
  → 우리 처리 중 화면: 결제 버튼을 누르면 버튼이 즉시 진행 상태로 바뀌고, 화면에 "카드사 승인을 기다리고 있습니다."를 적는다.
- GOV.UK Design System, "Confirmation pages" — https://design-system.service.gov.uk/patterns/confirmation-pages/
  완료 화면에 넣을 것: 참조 번호(있으면), 다음에 무엇이 언제 일어나는지, 연락처, 다음에 필요할 링크, 거래 기록을 저장할 방법(예: PDF). 완료 화면을 영수증처럼 즐겨찾기하는 사용자가 있으니 다시 열 수 있게 한다.
- GOV.UK Design System, "Check answers" — https://design-system.service.gov.uk/patterns/check-answers/
  제출 직전에 입력 내용을 구역별로 보여 주고 행마다 변경 링크를 둔다. 변경하러 가면 기존 값이 채워져 있고, 고친 뒤에는 확인 화면으로 바로 돌아온다. 입력하지 않은 선택 항목은 "Not provided"로 적는다. 제출 버튼 글자는 행동으로 쓴다.
- GOV.UK Design System, "Error summary" — https://design-system.service.gov.uk/components/error-summary/
  오류가 하나여도 요약 상자와 칸 옆 오류 문장을 둘 다 보여 준다. 요약은 본문 맨 위(뒤로 링크 아래, 제목 위)에 둔다. 요약의 각 줄은 해당 칸으로 연결하고 두 곳의 문장을 같게 쓴다. 화면이 다시 열리면 초점을 요약 상자로 옮기고, 페이지 제목 앞에 "Error: "를 붙인다.
- 견적 요청형 장바구니(B2B quote cart)를 다룬 Baymard · NN/g 공개 글: 확인한 글 없음(검색 1회에서 나오지 않았다).

## 7. 이 유형에 그대로 쓸 수 있는 문장

1. 장바구니 목록은 "상품 → 색상 → 사이즈 행" 3단으로 묶고, 사이즈 행 한 줄에 "사이즈 · − 수량 + · 삭제"를 둔다. 색상 묶음 머리줄 아래에 인쇄·포장 요약 한 줄과 "변경" 링크를 둔다.
2. 수량 입력은 PC에서 색상 행 × 사이즈 열 표로, 모바일에서 색상 하나를 고른 뒤 사이즈 3칸씩 줄바꿈한 칸으로 둔다. 표 아래에 사이즈별 합계와 총 수량을 적는다.
3. 장바구니 제목 옆에 총 수량을 적고("장바구니 (120벌)"), 제목 아래에 "1. 장바구니 > 2. 요청 정보 입력 > 3. 접수 완료" 3단계 표시를 둔다.
4. 목록 머리줄 한 줄에 "전체 선택 | 선택 삭제"를 두고, 요청 버튼 글자에 선택 건수를 넣는다("선택한 3개 상품 견적·시안 요청").
5. PC는 "목록 약 2/3 + 요약 약 1/3(스크롤을 따라 고정)" 2열, 모바일은 1열에 화면 아래 고정 띠("선택 3개 · 총 120벌" + 요청 버튼)로 둔다.
6. 정해지지 않은 금액은 0원으로 적지 않고 문장으로 적는다("인쇄비·배송비는 견적서에서 안내합니다.").
7. 상품별 수정은 "옵션/수량 변경" 버튼으로 PC는 가운데 창, 모바일은 아래 시트를 열고, 값이 바뀌기 전에는 "변경하기"를 비활성으로 둔다.
8. 주문서는 한 화면에 "주문자 → 배송지 → 배송방법 → 희망배송일 → 주문상품 → 포인트 → 결제수단 → 증빙서류 → 정책 동의 → 버튼" 순서로 쌓고, 위 메뉴는 빼고 로고와 화면 제목만 둔다.
9. 선택지(배송지 지정 방식 3종, 배송방법 4종, 결제수단 3종, 증빙서류 3종)는 드롭다운이 아니라 모두 펼친 선택지로 두고, 고른 선택지의 추가 입력칸을 그 바로 아래에 보여 준다. 배송방법 선택지는 왼쪽에 이름·조건, 오른쪽에 요금을 적는다.
10. 오류는 화면 위 요약 상자(오류 개수 + 오류마다 해당 칸으로 가는 링크)와 칸 바로 위에 같은 문장으로 보여 주고, 입력값은 지우지 않는다.
11. 수정 불가 구역(잔금 결제)은 입력칸 대신 "항목 이름 | 값" 요약 목록으로 보여 주고(모바일은 이름 → 값 세로 2줄), 구역 제목 옆에 바꿀 수 없는 이유와 문의 방법을 한 줄로 적는다.
12. 결제 버튼 글자에 금액을 넣고("1,040,000원 결제하기"), 누르면 즉시 진행 상태로 바꾸며 처리 중 화면에는 지금 하는 일을 글자로 적는다("카드사 승인을 기다리고 있습니다.").
13. 완료 화면은 "완료 문구 + 번호 → 확인 메일 발송 한 줄 → 다음 순서(번호 목록, 기준 시간 포함) → 요약 목록 → 버튼 2개" 순서로 두고, 요청 접수 완료에는 "결제는 아직 진행되지 않았습니다."를 적는다.
