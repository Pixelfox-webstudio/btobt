## 2. 남긴 곳

### 2-1. 무신사 마이

- 주소: https://www.musinsa.com/mypage
- 본 날짜: 2026-11-17
- 캡처: musinsa-my-pc.jpg, musinsa-my-m.jpg
- 종류: 실제 서비스 화면(로그인하지 않은 상태). 숫자는 모두 0이고 주문 단계별 건수는 나오지 않는다.

**관찰한 사실**

- PC에도 옆 메뉴가 없다. 1440 폭에서 가운데 약 960px 한 단에 모바일과 같은 순서로 놓인다. 양옆은 비어 있다.
- 위에서부터 순서: 화면 이름 "마이"와 오른쪽 아이콘 3개(알림·설정 등, 모바일은 장바구니까지 4개) → 혜택 한 줄과 "로그인/회원가입하기" 링크 → 요약 카드 → 메뉴 목록.
- 요약 카드는 3칸이고 칸 사이를 세로 선으로 나눈다: 적립금 0원 / 무신사머니 / 쿠폰 0장. 칸마다 이름 뒤에 ">"가 붙어 해당 내역으로 간다. 같은 카드 아랫줄에 "작성 가능한 후기 0개 >" 한 줄이 따로 있다.
- 메뉴는 19줄이고 가로 선으로 4묶음이 된다. 묶음에 제목은 없다.
  - 1묶음(6줄): 주문 내역, 취소/반품/교환 내역, 재입고 알림 내역, 최근 본 상품, 무신사 USED, 이벤트/회원혜택
  - 2묶음(6줄): 나의 맞춤 정보, 개선 의견/리서치 참여, 체험단 신청/응모 내역, 래플 응모 내역, 크리에이터 마켓플레이스, 무신사 큐레이터 서비스
  - 3묶음(3줄 + 띠 1개): 상품권/교환권 등록, 무신사페이 관리, 제휴카드, 그 아래 카드 홍보 띠
  - 4묶음(4줄): 고객센터, 1:1 문의 내역, 상품 문의 내역, 공지사항
- 한 줄은 왼쪽에 메뉴 이름, 오른쪽 끝에 화살표이고 아이콘은 없다. 새로 생긴 메뉴 6개는 이름 바로 뒤에 "신규" 표식이 붙는다. 건수 숫자는 없다(로그인 전).
- 주문과 관련된 두 줄(주문 내역, 취소/반품/교환 내역)이 목록의 맨 위에 있고, 문의와 관련된 줄은 맨 아래 묶음에 모여 있다.
- 모바일에서 달라지는 점: 맨 위에 앱 열기 띠가 생긴다. 화면 아래에 5칸 고정 탭(브랜드·스냅·홈·좋아요·마이)이 있고 "마이"가 선택 상태다. 본문 순서와 묶음은 PC와 같다. PC에는 고정 탭이 없고 상단 메뉴의 "마이"로 들어온다.

**가져올 것**

- 회원 요약을 맨 위 한 장으로 두고, 숫자 칸마다 ">"를 붙여 해당 목록으로 바로 보낸다. 이유: 요약이 읽기만 하는 숫자가 아니라 이동 수단이 된다.
- 요약 카드 아랫줄의 "작성 가능한 후기 N개 >" 같은 한 줄짜리 할 일 링크. 우리는 "확인할 시안 N건 >"을 이 자리에 둔다. 이유: 숫자 칸과 섞지 않고 한 줄로 떼어 두어 행동이 필요한 것만 따로 읽힌다.
- 메뉴를 한 줄에 하나씩, 묶음 사이는 선 하나로 나누고 주문 관련 줄을 맨 위에 두는 순서.
- 모바일 아래 고정 탭에 마이페이지 진입을 두는 것(우리 홈의 모바일 하단 띠에 이미 자리가 있다).

**바꿔서 쓸 것**

- PC 한 단 구조는 가져오지 않고 묶음 순서만 가져온다. 우리는 13부분을 오가며 쓰므로 PC는 옆 메뉴 + 본문 2단으로 하고, 무신사의 묶음을 옆 메뉴에 옮긴다. 모바일은 무신사와 같이 첫 화면을 요약 + 메뉴 목록으로 한다.
- 묶음에 제목을 붙인다(주문·견적 / 문의 / 혜택 / 내 정보). 이유: 캡처에서는 묶음 4개가 선으로만 나뉘어 묶음 기준을 글자로 확인할 수 없었다. 우리 메뉴는 13줄 안팎이라 제목 4개를 넣어도 한 화면에 들어온다.
- "신규" 표식 자리에 처리할 건수를 넣는다(예: 견적문의 내역 2). 이유: 우리가 알려야 하는 것은 새 메뉴가 아니라 새 답변·새 시안이다.
- 요약 3칸은 포인트 / 진행 중 주문 / 답변 온 문의로 바꾼다.

**쓰지 않을 것**

- 메뉴 목록 사이의 홍보 띠와 맨 위 앱 열기 띠. 이유: 구매 담당자가 마이페이지에서 하는 일(주문·견적·시안 확인)과 관계가 없고 메뉴 줄 사이를 끊는다.
- 서비스 소개 성격의 메뉴 줄(2묶음 대부분). 우리에게 해당 기능이 없다.
- 이 화면을 주문 단계별 건수의 근거로 쓰지 않는다. 로그인 전이라 그 부분이 화면에 없다.

### 2-2. 레드프린팅 고객센터 자주 묻는 질문

- 주소: https://www.redprinting.co.kr/ko/board/faq/lists
- 본 날짜: 2026-11-17
- 캡처: redprinting-faq-pc.jpg, redprinting-faq-m.jpg ("회원 탈퇴는 어디서 하나요?" 줄을 눌러 펼친 상태)
- 종류: 실제 서비스 화면. 인쇄물 주문 제작 쇼핑몰이라 시안·제작 흐름이 우리와 가깝다. 마이페이지 자체는 로그인이 필요해 보지 못했고, 같은 틀(옆 메뉴 + 목록)을 쓰는 고객센터 화면을 보았다.

**관찰한 사실**

- PC는 2단이다. 왼쪽 옆 메뉴 폭 약 160px, 사이 간격 약 56px, 오른쪽 본문 약 1,064px.
- 옆 메뉴 순서: 묶음 제목 "고객센터" → 6줄(홈, 공지사항, 자주 묻는 질문, 가이드, 이벤트, 서비스 약관) → 선 → 바깥으로 나가는 링크 3줄(디자인 서비스, 대량 주문상담, 회사소개. 줄 오른쪽에 새 창 아이콘) → 아래쪽에 고객센터 전화번호와 운영 시간 3줄. 현재 화면인 "자주 묻는 질문"만 굵다.
- 본문 순서: 화면 제목과 같은 줄 오른쪽에 검색 칸 → 분류 탭 7개(전체, 회원, 결제/입금/증빙, 접수/제작/주문, 배송, AS/취소/환불, 기타) → 목록 10줄 → 가운데 정렬 쪽 번호(1~5와 다음 화살표).
- 목록 한 줄은 3칸이다: 분류 이름(약 130px 폭) / 질문 / 오른쪽 끝 펼침 화살표. 줄을 누르면 페이지를 옮기지 않고 그 줄 바로 아래에 답변 영역이 본문 폭 전체로 펼쳐지고, 펼친 줄의 질문이 굵어지며 화살표가 뒤집힌다.
- 펼친 답변의 구성(탈퇴 안내): 첫 줄에 경로와 절차("마이페이지 › 회원정보 › 회원 탈퇴에서 유의사항 확인에 동의하고 비밀번호를 입력하면 바로 탈퇴") → "탈퇴 전 확인해 주세요!" → 항목 4개(회원 전용 서비스 중단과 같은 정보로 1개월 내 재가입 불가, 거래 기록은 법정 기간 보관, 작성한 문의·후기·댓글은 삭제되지 않음, SNS 연결은 따로 해제).
- 모바일에서 달라지는 점
  - 옆 메뉴가 없어지고 머리 부분이 "뒤로 화살표 + 가운데 화면 제목"으로 바뀐다.
  - 검색 칸이 제목 아래 한 줄을 다 쓴다.
  - 분류 탭은 한 줄에 4개까지만 보이고 나머지는 오른쪽으로 잘려 있다(가로로 밀어 보는 방식).
  - 목록에서 분류 칸이 빠지고 질문 + 화살표 2칸이 된다. 긴 질문은 2줄로 넘어간다.
  - 화면 아래에 5칸 고정 탭(카테고리·홈·가운데 로고·마이페이지·최근 본)이 있다.
- PC·모바일 모두 오른쪽 아래에 떠 있는 버튼 2개(상담, 맨 위로)가 있고, 캡처에서 PC는 펼침 화살표 열 위에, 모바일은 답변 글 위에 겹쳐 있다.

**가져올 것**

- 문의 목록에서 줄을 누르면 바로 아래에 답변이 펼쳐지는 방식. 견적문의 내역과 안전용품 문의에 쓴다. 이유: 답변 하나를 보려고 상세 화면을 오갈 필요가 없고 여러 건을 이어서 볼 수 있다.
- PC 옆 메뉴의 순서: 묶음 제목 → 메뉴 줄 → 선 → 다른 곳으로 나가는 줄 → 고객센터 전화·운영 시간. 현재 위치는 굵기로만 표시.
- 모바일에서 옆 메뉴를 없애고 머리 부분을 "뒤로 + 화면 제목"으로 바꾸는 전환.
- 모바일에서 분류 탭을 한 줄로 두고 가로로 미는 방식(주문 단계 띠에 쓴다).
- 탈퇴 화면의 내용 순서: 유의사항 목록 → 동의 → 비밀번호 입력. 유의사항은 재가입 제한, 거래 기록 보관, 작성 글 처리처럼 탈퇴 뒤에 남는 것과 사라지는 것을 항목으로 적는다.

**바꿔서 쓸 것**

- 줄의 첫 칸을 분류 대신 답변 상태(답변 대기 / 답변 완료)로 바꾸고 작성일 칸을 더한다: [답변 상태][제목][작성일][화살표]. 모바일은 제목을 첫 줄에, 답변 상태와 작성일을 둘째 줄에 둔다(레드프린팅처럼 칸을 빼지 않는다. 답변 상태는 빼면 안 되는 정보다).
- 펼친 영역에는 내 문의 원문 → 답변(답변일 포함) 순으로 넣고, 시안이 붙은 견적문의는 답변 아래에 "시안 보기" 버튼을 둔다.
- 분류 탭 자리에 답변 상태 탭(전체 / 답변 대기 / 답변 완료)을 두고 이름 뒤에 건수를 붙인다.

**쓰지 않을 것**

- 맨 위 공지 띠. 마이페이지에는 두지 않는다.

### 2-3. KRDS 구조화 목록 · 필터링·정렬

- 주소: https://www.krds.go.kr/html/site/component/component_04_01.html (구조화 목록), https://www.krds.go.kr/html/site/global/global_10.html (필터링·정렬)

**관찰한 사실 — 구조화 목록**

- 목록 화면을 4부분으로 정의한다: ① 제목(선택) ② 도구 막대(선택: 검색, 필터, 정렬, 더보기 링크, 액션 버튼) ③ 항목(선택 체크박스, 미리보기 이미지, 콘텐츠, CTA, 액션 버튼, 항목 구분자) ④ 페이지네이션(선택).
- 리스트형 그림: 제목 → 한 줄 도구 막대(왼쪽 전체선택, 오른쪽 핵심 버튼 4개 · 목록 표시 개수 선택 · 정렬 기준 3개) → 항목 카드. 항목 카드 안은 표식 → 제목(뒤에 ">") → 설명 한 줄 → 메타 정보 한 줄(세로 선으로 구분한 5~6개), 오른쪽 위에 행동 2개 → 아래 가운데 쪽 번호(이전, 1~8, …, 99, 다음).
- 표형 그림: 같은 도구 막대 아래에 표(선택, 유형, 제목, 내용, 행동 링크, 게시일 열)와 쪽 번호.
- 사용성 지침 글 4개: 도구 막대는 모든 화면에서 같은 위치·같은 순서로 둔다 / 항목에서 가장 중요한 행동 하나를 가장 강한 버튼으로 둔다 / 사용자가 자주 쓰는 기능과 행동 버튼을 항목에 준다 / 항목의 정보는 모든 항목에서 같은 분류와 순서로 주고, 값이 없는 자리는 비우지 말고 대시(-)를 넣는다.
- 모바일에서 달라지는 점(문서 자체): 왼쪽 문서 메뉴가 "전체메뉴" 버튼 뒤로 들어가고, 본문이 한 단이 되며, 그림은 폭에 맞게 줄어든다. 목록 구성의 모바일 형태는 캡처한 범위(위 4,500px)에 나오지 않았다.

**관찰한 사실 — 필터링·정렬**

- 구조 4부분: ① 정렬 컨트롤 ② 필터 컨트롤(기본으로 보이거나 상세 필터 버튼으로 엶) ③ 적용된 필터링 조건(조건, 조건 수, 해당 항목 개수, 조건별 해제 버튼) ④ 적용된 조건 전체 해제 버튼.
- 필터 방식 6가지: 텍스트, 스코프(선택 칸 + 입력 칸 + 검색 버튼), 선택형(이름표 + 선택 칸을 한 줄에 3개), 범위(시작날짜·종료날짜 두 칸, 입력 형식 YYYY.MM.DD), 쿼리, 관계형.
- 조회 방식 2가지: 즉각 표시(고르자마자 반영. 한 번에 1~2개 속성만 고르고 조회가 빠를 때) / 일괄 표시(고른 뒤 '조회하기'·'적용하기'를 눌러야 반영. 조건이 복잡하거나 조회가 느릴 때).
- 배치 3가지: 수평 막대(목록 위에 얇고 긴 막대), 인라인(표의 열 머리에 직접), 사이드 패널. 수평 막대 그림에는 선택 칸 3개 → 선택된 조건 칩 줄 → "검색 결과 N개"와 표시 개수·정렬 → 3열 카드 목록 순서가 보인다.
- 모바일에서 달라지는 점(문서 자체): 구조화 목록 문서와 같다. PC 캡처는 5,200px에서 끊겨 "사용성 가이드라인" 절은 찍히지 않았다.

**가져올 것**

- 목록 화면의 부분 순서 "제목 → 도구 막대 → 항목 → 쪽 번호"를 주문 내역, 견적문의 내역, 안전용품 문의, 관심상품, 포인트 내역 다섯 화면에 똑같이 쓴다. 이유: 지침이 도구 막대의 위치와 순서를 화면마다 같게 두라고 한다.
- 항목 안 순서 "표식 → 제목(상세로 가는 링크) → 설명 → 메타 정보 한 줄 / 오른쪽에 행동". 주문 한 건에 그대로 대응한다(상태 표식 → 대표 상품 이름 → 상태 설명 → 주문번호 | 주문일 | 수량 | 금액 / 오른쪽 버튼).
- 항목마다 가장 중요한 행동 하나만 가장 강한 버튼으로 둔다(상태별 버튼 규칙의 근거).
- 값이 없는 칸에 "-"를 넣는다(포인트 표의 사용 칸, 송장번호 등).
- 주문은 리스트형, 포인트 내역은 표형으로 나눈다.
- 기간은 시작일·종료일 두 칸으로 받는다.
- 적용된 조건을 목록 바로 위에 "조건 + 해당 건수"로 다시 보여 준다(예: "제작중 · 최근 3개월 · 3건").
- 즉각 표시와 일괄 표시의 구분: 단계 띠와 빠른 기간 버튼은 누르면 바로 반영하고, 날짜를 직접 고쳤을 때만 "조회" 버튼을 쓴다.
- 필터 배치는 수평 막대(목록 위)로 한다.

**바꿔서 쓸 것**

- 전체선택 체크박스는 주문·문의 목록에서 뺀다(여러 건을 한꺼번에 처리하는 동작이 없다). 관심상품에만 두고 "선택 삭제", "선택 상품 장바구니 담기"와 짝지운다.
- 쪽 번호는 그림의 1~99 대신 한 번에 5개와 이전/다음만 보인다. 기간 필터로 건수가 먼저 줄어든다.
- 표식 자리에 주문 상태를 넣고 오른쪽 위 행동 2개 자리에 상태별 버튼 줄을 넣는다.

**쓰지 않을 것**

- 쿼리 필터, 관계형 필터, 사이드 패널. 이유: 우리 조건은 단계와 기간 둘뿐이다.
- 그림의 치수와 간격. 안내 문서의 구성도라 실제 화면 근거가 아니다.

**관찰한 사실 — 주문 목록(표형)**

**가져올 것**

- PC 2단과 옆 메뉴의 순서(계정 이름 → 메뉴 → 선 → 설정·로그아웃). 로그아웃을 맨 아래 선 밑에 따로 둔다.

- 상태별 버튼 규칙 세 가지: 해당 없는 버튼은 그리지 않는다 / 강조 버튼은 한 건에 1개 / "주문 상세"는 모든 상태에서 같은 자리.
- 빠른 기간 옆에 실제 날짜 범위를 같이 보여 주는 것. 이유: "최근 3개월"이 며칠부터인지 확인하려고 달력을 열 필요가 없다.
- 계정 개요의 순서: 숫자 칸 → 내 정보(이름표: 값) + 수정 버튼 → 진행 중 주문 몇 건 + "전체 보기" → 기본 배송지 카드 + 수정 버튼.
- 수정 양식의 규칙: 이름표는 칸 위, 필수는 *, 관련된 두 항목은 PC에서 한 줄 2칸·모바일에서 1열, 버튼은 저장(강조) → 취소 순.
- 배송지 양식 맨 위의 "저장된 주소에서 고르기" 선택 칸. 견적·주문 화면에서 배송지를 고를 때도 같은 방식으로 쓴다.
- 확인 창의 구성: 질문 한 문장 → 되돌릴 수 없다는 한 줄 → 버튼 2개.
- 표형에서 건수 문장("1-10 / 전체 1000")을 쪽 번호 옆에 두는 것.

**바꿔서 쓸 것**

- 상태 고르기를 선택 칸("Filter by") 대신 건수가 붙은 단계 띠로 바꾼다(3장 shadcn 참고). 이유: 선택 칸은 열기 전에는 단계별 건수가 보이지 않는다. 우리가 풀어야 하는 것은 건수를 보이는 것이다.
- 기간 선택 6줄을 선택 칸 안에 숨기지 않고 빠른 기간 버튼 4개(1개월·3개월·6개월·1년)로 꺼내고, 날짜 범위는 옆의 시작일·종료일 두 칸에 채워 보여 준다.
- 모바일 버튼 쌓기를 줄인다. 강조 버튼 1개만 가로를 다 쓰고, 나머지 버튼(주문 상세 등)은 그 아래 한 줄에 나란히 둔다. 이유: 캡처에서 버튼 3개를 세로로 쌓은 주문 한 건이 화면 높이의 절반을 넘었다.
- 모바일 표는 가로로 밀지 않게 한다. 포인트 내역은 모바일에서 한 건을 2줄(첫 줄 내용과 적립·사용 금액, 둘째 줄 날짜와 잔액)로 바꾼다. 이유: 캡처에서 상태 열과 줄 끝 버튼이 화면 밖으로 나가 있었다.
- 회원정보 수정은 창이 아니라 화면 하나로 만든다(항목이 더 많고 비밀번호 확인이 앞에 붙는다). 배송지 추가·수정은 항목이 5~6개이므로 이 창 방식을 쓴다.
- 확인 창의 버튼 이름을 "예/아니오" 꼴 대신 결과로 적는다("탈퇴하기" / "계속 이용하기", "주문 취소하기" / "닫기"). 근거는 5장의 NN/g 글.
- 계정 개요의 숫자 4칸은 진행 단계별 주문 건수로 바꾼다.

**쓰지 않을 것**

- 모바일에서 옆 메뉴가 사라지고 대신할 것이 없는 방식. 캡처에서 다른 메뉴로 갈 길이 화면에 없다.
- 주문 카드의 이메일 줄(모든 주문에 같은 값이 반복된다)과 요금제·설문·포인트 진행 카드(우리에게 없는 내용).
- 줄마다 "Actions" 펼침 버튼이나 "…" 버튼 뒤에 행동을 숨기는 방식. 우리는 상태별 버튼을 바로 보여야 한다.
- 문구와 숫자. 견본 값이다(기간 선택의 날짜 범위도 견본이라 앞뒤가 맞지 않는 줄이 있다).

**관찰한 사실 — 포털 첫 화면(소개 그림)**

- PC 2단. 옆 메뉴 9줄: Home, Activity, Orders, Quotes, Jobs, Approvals, Messages, Invoices, Shipments. 9줄 가운데 Approvals 한 줄에만 오른쪽에 건수 "2"가 붙는다. 옆 메뉴 맨 아래에 고객 회사 이름과 설정 아이콘.
- 본문 순서: 화면 제목과 오른쪽 "잔액 명세 내려받기" 버튼 → 금액 4칸 한 줄(사용 가능 예치금, 내야 할 계약금, 미수금, 연체액. 칸마다 아랫줄에 해당 목록으로 가는 작은 링크) → "Requires your attention 2" 목록(오른쪽에 "Approvals →") → 2열(왼쪽 최근 활동, 오른쪽 최근 주문).
- "Requires your attention" 한 줄: 아이콘 또는 상품 썸네일 → 대상 이름(견적 번호 / 작업 이름) → 필요한 행동 한 줄("Approval needed before work is scheduled", "Artwork approval needed · Sales Order SO0001") → 오른쪽에 요청일과 "today" → 화살표.
- 최근 주문 한 줄: 주문번호 — 발주번호, 금액, 상태(점 + 이름: Delivered, Shipped, Ready to Ship, In Production).
- 그림 안 휴대폰 화면: 금액 4칸이 2×2가 되고, 그 아래 "Requires your attention" 목록, 화면 아래 고정 탭 5칸(Home, Orders, Approvals, Messages, More). Approvals 탭에 건수 표식이 붙는다. 옆 메뉴 9줄 가운데 4줄이 탭으로 나오고 나머지는 More 뒤로 간다.

**관찰한 사실 — 주문 상세(소개 그림)**

- 머리 부분: 뒤로 화살표 + "Sales order SO0001" + 상태 표식, 아랫줄에 발주번호와 작은 표식 2개(진행 단계 "Artwork Review", 결제 "Balance due"). 같은 줄 오른쪽에 버튼 3개(Print, Message, Pay now 강조).
- 그 아래 "Jump to · Overview" 선택(화면 안 구역으로 건너뛰기).
- 본문 2단(왼쪽 약 3분의 2, 오른쪽 약 3분의 1).
  - 왼쪽 순서: 개요(주문 상태 / 주문 승인 / 결제 3칸, 그 아래 일정: 발행일·납기일, 청구: 발주번호·결제 기한. 날짜 뒤에 "9일 전", "9일 뒤" 같은 상대 표현) → "Action required 1" 띠(썸네일 + "Artwork approval needed" + Review 버튼) → 작업 목록(작업 이름, 수량·금액, 상태 표식 2개, 접기, View job. 작업 안에도 "Review artwork" 알림 줄과 Review 버튼) → 작업 명세 표(번호, 작업 방식, 옵션, 위치) → 상품 명세 표(번호, 상품, 수량, 단가, 소계, 합계 줄) → 시안 파일 목록(썸네일, 이름, 상태 표식, 날짜, Download 버튼).
  - 오른쪽 순서: 금액(수량, 소계, 배송, 할인, 세금, 합계, 낸 금액, 남은 금액, Pay now 버튼) → 청구서(금액, 기한, Unpaid 표식) → 입금 내역 → 메시지(보낸 사람, 날짜, 첫 두 줄).
- 그림 안 휴대폰 화면: 한 단. 머리 부분 → 버튼 줄(아이콘 2개 + Pay now) → Jump to → 개요 → 일정 → 청구 → "Action required" 띠 순으로 세로로 이어진다.

**관찰한 사실 — 시안 확인 흐름(도움말의 실제 화면 그림)**

- 들어가는 길 3가지: 승인 요청 메일의 링크 / 주문 상세의 "Action required" 띠나 작업 줄에 있는 Review 버튼 / 옆 메뉴 Approvals.
- Approvals 목록: 위에 "Results per page 25", 검색 칸, Filter, Sort. 표의 열은 이름, 종류(Artwork), 주문·견적 번호(링크), 요청일, 열람 상태. 이름 아래에 "2 items to review"가 작은 줄로 붙는다.
- 시안 확인 창(PC): 화면 위에 뜨는 큰 창. 머리 부분에 작업 이름, 주문번호 · 작업번호, 요청일. 그 아래 3단.
  - 왼쪽: "Reviewed: 0 / 2" 줄과 시안 목록(썸네일 + 파일 이름 + 종류). 결정한 시안에는 썸네일에 표시가 붙고 숫자가 1 / 2, 2 / 2로 오른다.
  - 가운데: 시안 이름 → 가게가 적은 메모("앞면 인쇄, 폭 8인치. 구단 이름, 색, 가운데 정렬을 확인해 주세요") → 큰 시안 이미지.
  - 오른쪽: 질문 "Do you approve this artwork?" → 선택 카드 2개("Approve artwork — 서명 뒤에 제출됩니다" / "Request changes — 고칠 점을 적어 주세요. 적어야 검토한 것으로 셉니다").
  - 오른쪽 아래: "Next artwork" 버튼.
- "Request changes"를 고르면 그 카드 바로 아래에 "Describe the changes" 입력 칸이 나타난다. 비워 두고 Next artwork를 누르면 칸에 오류 표시가 생기고 칸 아래에 "Describe the requested changes before continuing."이 나오며, 그 시안은 검토하지 않은 것으로 남는다(왼쪽 숫자가 오르지 않는다).
- 모든 시안에 결정을 내리면 버튼이 "Continue to sign"으로 바뀐다.
- 서명 단계: 한 줄 요약("Approving 1 artwork, requesting changes on 1") → 약관 글 → "Signed by" 입력 칸(이름을 치는 것이 서명) → 버튼 2개("← Back to review", "Submit decision"). Back to review로 돌아가도 고른 내용은 남는다.
- 제출 뒤: 작은 확인 창 "Your decision was sent to the shop" + Done. 같은 주문에 남은 승인이 있으면 "1 more approval on this order"와 함께 버튼이 Done / "Review next" 2개가 된다. 끝난 요청은 대기 목록에서 빠진다.
- 휴대폰 화면: 창이 화면 전체를 쓴다. 위에서부터 창 제목과 닫기 → "← Back to artwork list" → 시안 이름과 종류 → 메모 → 시안 이미지 → 질문 → 선택 카드 2개(세로) → 화면 아래에 가로를 다 쓰는 "Next artwork" 버튼. 시안 목록은 같은 화면에 없고 "Back to artwork list"로 가는 별도 화면이다. 시안 한 장이 한 화면이다.

**관찰한 사실 — 견적 승인(소개 그림)**

- "Requires your attention"의 견적 줄에서 들어간다. 질문 "Do you approve this quote?"와 선택 2개(Approve quote / Request changes). 수정 요청을 고르면 "Describe the changes" 입력 칸, 승인을 고르면 약관("승인하면 수량, 작업 방식, 납기일이 확정되고 계약금 50%를 내면 제작을 시작합니다")과 "Signed by" 칸이 나온다. 시안 승인과 같은 질문·선택 구조다.

**가져올 것**

- "확인할 일" 목록을 주문 목록보다 위, 회원 요약 바로 아래에 둔다. 한 줄에 "대상 이름 + 필요한 행동 한 줄 + 요청일 + 화살표". 이유: 구매 담당자가 들어와서 가장 먼저 해야 하는 것은 시안 확인·견적 확인·입금이고, 이 목록이 그 세 가지를 한곳에 모은다.
- 건수 표식을 메뉴 전체가 아니라 처리할 일이 있는 줄에만 붙인다(Approvals 한 줄에만 "2").
- 주문 상세에서 "해야 할 일" 띠를 개요 바로 아래에 두고 띠 안에 버튼 하나(시안 확인)를 넣는다. 띠는 해야 할 일이 있을 때만 나온다.
- 주문 상세의 순서: 머리 부분(주문번호 + 상태 표식 + 버튼) → 개요(상태·일정·결제) → 해야 할 일 → 상품·작업 명세 표 → 시안 파일 목록(내려받기). PC는 금액과 결제를 오른쪽 열에 따로 둔다.
- 날짜 옆에 "9일 뒤" 같은 상대 표현을 붙이는 것(납기일, 입금 기한).
- 시안 확인 화면의 3단과 질문·선택 2개 구조, 왼쪽의 "검토 N / 전체" 숫자.
- 수정 요청을 골랐을 때만 입력 칸이 나오고, 비우면 넘어가지 못하며 칸 아래에 이유를 적는 방식.
- 시안마다 결정만 모아 두고 마지막에 한 번 제출하는 2단계(결정 → 요약 확인 후 제출). 제출 전 "승인 N건, 수정 요청 N건" 한 줄 요약과 "검토로 돌아가기".
- 제출 뒤 확인 창에서 남은 승인이 있으면 "다음 검토"로 바로 잇는 것.
- 모바일에서 시안 한 장을 한 화면으로 하고 "다음 시안" 버튼을 화면 아래에 고정하는 것.
- 주문 상세·확인할 일·메뉴 세 곳 모두에서 시안 확인으로 들어갈 수 있게 하는 것.
- 견적문의 시안 보기에도 같은 질문·선택 구조를 그대로 쓴다(주문 시안과 견적 시안의 화면을 따로 만들지 않는다).

**바꿔서 쓸 것**

- 이름을 쳐서 서명하는 칸은 빼고, 요약 한 줄 → 안내 글("승인하면 제작이 시작되어 시안을 바꿀 수 없습니다") → 확인 체크 1개 → "제출하기"로 바꾼다. 우리 주문 절차에 서명 항목이 없다.
- 시안이 1장뿐인 주문은 왼쪽 목록 단을 없애고 2단(이미지 | 질문)으로 한다. 2장 이상일 때만 3단으로 한다.
- 금액 4칸 자리에 진행 단계별 주문 건수를 둔다. 예치금·연체 같은 항목은 우리에게 없다.
- 옆 메뉴 9줄은 우리 13부분과 맞지 않으므로 줄 구성은 2-1의 묶음을 쓰고, 건수를 붙이는 방식만 가져온다.
- 큰 창 대신 화면 하나(시안확인 페이지)로 만든다. 메일·문자의 링크로 바로 들어오는 화면이므로 주소가 있어야 한다.
- 시안 이미지는 누르면 원본 크기로 볼 수 있게 한다(소개 그림의 "맞춤 / 100%" 전환을 단순하게).

**쓰지 않을 것**

- 3D 미리보기, 최근 활동 시간순 목록. 이유: 우리 쪽에 그 데이터가 없다.
- Jobs·Invoices·Shipments를 따로 나눈 메뉴. 우리는 주문 한 건 안에서 다 본다.
- 소개 페이지 그림 4장을 동작의 근거로 쓰는 것. 꾸민 그림이라 실제와 다를 수 있다. 동작은 도움말 그림에서 확인한 것만 적었다.

## 4. 우리 문제마다 어느 화면이 답하는가

- 주문 단계별 건수와 그 단계만 골라 보기 → shadcn(이름 뒤 건수가 붙은 띠), Flowbite 표형(한 줄 고르기 4개), KRDS 필터링·정렬(적용된 조건과 해당 건수 표시, 바로 반영).
- 주문마다 상태에 따라 달라지는 버튼 → Flowbite 주문 카드(진행 중 3개 / 끝난 주문 2개, 강조 1개), Shopify 주문 목록 그림(결제 필요 시 1개만, 넷째부터 접기), KRDS(가장 중요한 행동 하나만 가장 강하게).
- 조회 기간 + 빠른 기간 → Flowbite 기간 선택(6줄, 실제 날짜 범위를 옆에), KRDS 범위 필터(시작일·종료일 두 칸)와 즉각/일괄 표시 구분. 국내 쇼핑몰의 "1개월·3개월·6개월 버튼 + 날짜 두 칸" 실제 화면은 찍지 못했다.
- 메뉴 묶음과 새 소식 수 → 무신사(4묶음, 이름 뒤 표식), YoPrint(처리할 일이 있는 메뉴에만 건수, 모바일 탭에도 건수).
- 시안 이미지를 보고 승인 또는 수정 요청 → YoPrint 도움말(전체 흐름), Sticker Mule(4단계와 제작 조건 문장).
- 문의 내역에서 답변 펼쳐 보기 → 레드프린팅.
- 배송지 목록·추가·수정 → Flowbite 계정 개요의 기본 배송지 카드와 수정 버튼, 수정 창의 "저장된 주소 고르기 + 입력 칸". 배송지 여러 개를 늘어놓은 목록 화면과 추가 화면은 찍지 못했다.
- 포인트 적립/사용 표 → 직접 본 화면이 없다. KRDS 표형 구조(도구 막대 → 표 → 쪽 번호)와 "빈 칸은 -" 지침만 있다.
- 회원정보 수정 양식 → Flowbite 수정 창(7항목, 필수 표시, PC 2칸·모바일 1열, 저장 → 취소).
- 탈퇴 확인 → 레드프린팅 탈퇴 안내 글(유의사항 4항목 → 동의 → 비밀번호), Flowbite 확인 창(질문 → 되돌릴 수 없음 → 버튼 2개). 탈퇴 화면 자체는 찍지 못했다.
- PC 옆 메뉴와 모바일 전환 → 레드프린팅(옆 메뉴 → "뒤로 + 제목" 머리 부분, 아래 고정 탭), YoPrint(옆 메뉴 9줄 → 아래 탭 5칸 + More), 무신사(PC도 한 단), Flowbite(모바일에서 메뉴가 사라짐. 따라 하지 않을 예).

## 5. 사용성 근거

아래 1~4는 2026-11-17에 해당 주소의 글을 열어 내용을 확인했다(본문 전체를 옮긴 것이 아니라 요지다). 5~6은 캡처한 화면의 글에서 읽었다.

1. Baymard Institute, "Accounts & Self-Service UX 2025: 5 Common Pitfalls & Best Practices" (2024-06-11 게시, 2025-08-14 갱신) — https://baymard.com/research-articles/current-state-accounts-selfservice
   - 계정 메뉴에 핵심 경로 7개(대시보드, 주문, 결제수단, 적립·혜택, 관심상품, 배송지, 비밀번호)로 가는 직접 링크를 둔다. 글에 따르면 조사한 사이트의 96%가 이를 지키지 않는다. 메뉴를 심하게 줄이면 어떤 기능이 있는지 한눈에 보기 어려워진다.
   - 계정 첫 화면(대시보드)에서 모든 계정 기능에 갈 수 있어야 한다(78%가 지키지 않음). 대시보드가 있을 때 시험 참가자의 52%가 그것으로 기능을 찾아갔다.
   - 진행 중인 주문의 추적이 가장 중요한 셀프서비스 기능이다. 추적은 택배사 사이트로 보내지 말고 자기 사이트의 화면에서 도착 예정일, 택배사 이름, 세부 이동 기록을 보여 준다.
   - 취소를 요청한 주문에는 "취소 요청됨" 상태를 주문 내역, 주문 상세 등 주문이 보이는 모든 곳에 표시하고 확인 메일을 보낸다.
2. Baymard Institute, "145 'Orders Overview' Design Examples" — https://baymard.com/ecommerce-design-examples/62-orders-overview
   - 사용자가 주문 내역에 오는 이유는 여러 가지다. 글에 적힌 비율: 진행 중 주문 추적 50%, 반품 시작 26%, 지난 주문 확인 26%, 진행 중 주문 수정 19%, 취소 15%, 영수증·증빙 내려받기 8%.
   - 그래서 기본 주문 정보와 행동이 주문 목록에서 바로 보여야 한다. 없으면 주문 관리가 어려워지고 고객센터 부담이 는다고 적는다.
3. Nielsen Norman Group, Maria Rosala, "Status Trackers and Progress Updates: 16 Design Guidelines" (2019-02-03) — https://www.nngroup.com/articles/status-tracker-progress-update/
   - 진행 상황은 계정에서 찾을 수 있어야 한다 / 가장 최근 상태를 가장 먼저 보이게 한다 / 내부 용어·코드 대신 사용자가 아는 말로 쓴다 / 지난 상태를 날짜와 함께 남기고 자리가 모자라면 펼쳐 보게 한다 / 알림에서는 다시 번호를 넣지 않아도 해당 건으로 바로 가게 한다 / 오래 걸리는 단계에서는 중간 소식을 주기적으로 준다.
4. Nielsen Norman Group, Jakob Nielsen, "Confirmation Dialogs Can Prevent User Errors — If Not Overused" (2018-02-18) — https://www.nngroup.com/articles/confirmation-dialog/
   - 확인 창은 되돌릴 수 없고 결과가 큰 동작에만 쓴다. 일상적인 동작에 쓰면 읽지 않고 누르게 된다.
   - 질문은 무엇이 어떻게 되는지 구체적으로 적는다("정말 하시겠습니까?" 꼴을 피한다).
   - 버튼은 "예/아니오" 대신 결과를 적는다(글의 예: "Delete file" / "Keep file"). "예" 쪽을 기본 선택으로 두지 않는다.
   - 가장 위험한 동작은 단어를 직접 치게 하는 것 같은 평소와 다른 확인을 요구할 수 있다.
5. Shopify, "UX for customer accounts" — https://shopify.dev/docs/apps/build/customer-accounts/ux (캡처 shopify-account-ux-guide-pc.jpg 에서 읽음)
   - 상태 이름은 1~3단어 / 받은 뒤에만 뜻이 있는 행동(반품, 리뷰)은 배송 완료 전에는 못 하게 하는 것이 이상적 / 결제 상태에 따라 결제 카드를 주문 요약 위에 둔다 / 오류에는 사라지는 알림을 쓰지 않는다.
6. KRDS 구조화 목록, 필터링·정렬 — 주소와 내용은 2-3에 적었다(도구 막대의 위치·순서를 화면마다 같게, 가장 중요한 행동 하나를 가장 강하게, 빈 값은 "-", 즉각 표시와 일괄 표시의 구분).

확인하지 못한 것: 회원정보 수정 양식, 배송지 관리, 포인트 표에 대한 Baymard·NN/g 글은 열어 보지 않았다. 이 세 가지에 대해 확인한 글 없음.

## 6. 이 유형에 그대로 쓸 수 있는 문장

1. PC 마이페이지는 왼쪽 옆 메뉴 + 오른쪽 본문 2단으로 두고, 옆 메뉴는 "주문·견적 / 문의 / 혜택 / 내 정보" 네 묶음을 묶음 제목과 선으로 나누며, 처리할 일이 있는 줄(시안 확인, 견적문의 내역, 안전용품 문의)에만 이름 뒤에 건수를 붙이고 0건이면 숫자를 지운다. 로그아웃과 회원 탈퇴는 맨 아래 선 밑에 둔다.
2. 모바일에는 옆 메뉴를 그리지 않는다. 마이 첫 화면에 회원 요약 → 확인할 일 → 메뉴 목록(한 줄에 메뉴 하나, 오른쪽 끝 화살표, 줄 전체가 누르는 영역)을 세로로 두고, 하위 화면의 머리 부분은 "뒤로 + 화면 제목"으로 바꿔 첫 화면으로 돌아오게 한다.
3. 회원 요약 바로 아래에 "확인할 일" 목록을 둔다. 한 줄은 [상품 썸네일][주문·견적 이름][필요한 행동 한 줄: 시안 확인 필요 / 입금 대기 / 견적서 도착][요청일][화살표]이고, 할 일이 없으면 목록 자리에 "확인할 일이 없습니다." 한 줄만 둔다.
4. 주문 내역 위에 단계 띠를 둔다. "전체 12 · 결제전 1 · … · 구매확정 4"처럼 "전체"를 맨 앞에 두고 단계 이름 뒤에 건수를 붙이며, 하나를 누르면 조회 버튼 없이 바로 그 단계만 보인다. 모바일에서는 한 줄로 두고 가로로 민다. 목록 바로 위에 "제작중 · 최근 3개월 · 3건"처럼 적용된 조건과 건수를 다시 적는다.
5. 조회 기간은 빠른 기간 버튼 4개(1개월·3개월·6개월·1년)와 시작일·종료일 두 칸을 한 줄에 둔다. 빠른 기간을 누르면 두 칸에 실제 날짜가 채워지면서 바로 조회되고, 날짜를 직접 고쳤을 때만 "조회" 버튼을 누른다. 모바일은 버튼 한 줄, 날짜 한 줄로 나눈다.
6. 주문 한 건은 네 줄로 쓴다: ① 상태 표식 + 주문번호 + 주문일 ② 대표 상품 썸네일과 이름 "외 N건", 수량, 금액 ③ 상태를 풀어 쓴 한 줄("시안 확인을 기다리고 있습니다", "11월 20일 도착 예정") ④ 버튼 줄. 값이 없는 칸(송장번호 등)은 비우지 않고 "-"를 넣는다.
7. 버튼은 상태마다 강조 버튼을 하나만 둔다(결제전 → 결제진행, 견적 도착 → 견적서 보기, 시안 도착 → 시안 확인, 배송중 → 배송조회, 배송완료 → 구매확정, 구매확정 → 리뷰 쓰기). 그 상태에 해당하지 않는 버튼은 흐리게 두지 않고 그리지 않으며, "주문 상세"는 모든 상태에서 같은 자리에 둔다. 모바일에서는 강조 버튼만 가로를 다 쓰고 나머지는 그 아래 한 줄에 나란히 둔다.
8. 시안 확인 화면은 PC 3단(왼쪽 시안 목록과 "검토 2 / 3" · 가운데 담당자 메모와 시안 이미지 · 오른쪽 질문 "이 시안으로 제작할까요?"와 선택 2개 "승인" / "수정 요청")으로, 모바일은 시안 한 장을 한 화면으로 하여 이름 → 메모 → 이미지 → 질문 → 선택 2개 순서에 "다음 시안" 버튼을 화면 아래에 고정한다. 시안이 1장이면 왼쪽 목록 단을 뺀다. 화면 위쪽에 "모든 시안을 승인해야 제작이 시작됩니다."를 적는다.
9. "수정 요청"을 고르면 그 선택 바로 아래에 수정 내용 입력 칸이 나타나고, 비어 있으면 다음으로 넘어가지 않으며 칸 아래에 "수정할 내용을 적어 주세요."를 보인다. 모든 시안에 결정을 내린 뒤에만 제출 단계로 가고, 제출 전에 "승인 1건, 수정 요청 1건"을 한 줄로 다시 보여 주며 "검토로 돌아가기"를 눌러도 고른 내용은 남는다.
10. 문의 내역(견적문의, 안전용품 문의)은 한 줄에 [답변 상태][제목][작성일][펼침 화살표]를 두고, 줄을 누르면 페이지를 옮기지 않고 바로 아래에 문의 원문 → 답변(답변일) 순으로 펼친다. 시안이 붙은 견적문의는 답변 아래에 "시안 보기" 버튼을 둔다.
