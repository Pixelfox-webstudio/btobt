# 비투비티 하위 페이지 디자인 작업 지시

## 1. 무슨 일인가

비투비티는 주식회사 노을상사의 B2B 쇼핑몰이다. 기업과 관공서 구매 담당자에게 단체복·작업복·협력 브랜드 상품과 맞춤 작업복을 판다. 결제보다 장바구니에서 견적·시안 요청으로 넘어가는 흐름이 중심이다.

홈 화면은 이미 새로 디자인했다. 지금 이 폴더(`~/Downloads/b2bt-home-v10`)가 그 시안이고, `DESIGN.md`가 그 시안에서 뽑은 디자인 시스템이다. 이번 일은 **홈을 뺀 나머지 페이지 전부를 같은 디자인으로 새로 디자인해서, 이 폴더에 정적 HTML 시안으로 만드는 것**이다.

결과물은 사장님이 브라우저로 열어 보고 "이대로 개발하자"고 정할 수 있는 수준이어야 한다. 서버 연결과 실제 동작(PHP)은 이번 범위가 아니다. 화면 안에서 필요한 조작(선택, 수량 입력, 펼치기, 상태 바꿔 보기)만 JS로 붙인다.

사장님은 작업 중에 자리에 없다. 질문하지 말고 가장 무난한 해석으로 끝까지 진행하고, 결정이 필요했던 곳은 `spec/questions.md`에 적어 둔다.

## 2. 자료와 우선순위

위에 있을수록 우선한다.

1. **이 문서.**
2. **`spec/page-elements.md` — 페이지마다 있어야 하는 요소.** 무엇이 있어야 하는지만 적은 목록이다. 위치·순서·모양은 일부러 뺐다. 배치와 형태는 네가 새로 정한다. 이 목록의 요소는 하나도 빠지면 안 된다. 목록에 없는 기능을 새로 만들어 넣지도 않는다. "화면 없는 것" 절은 디자인 대상이 아니다.
3. **`DESIGN.md`, `index.html`, `css/` — 어떻게 보여야 하는가.** 색·글자·간격·모서리·문구 말투는 `DESIGN.md`가 정답이다. 폴더의 `CLAUDE.md`도 따른다.
4. **네가 직접 조사할 레퍼런스 — 구조와 흐름을 어떻게 풀 것인가.** 3절 참고.

`DESIGN.md`의 "페이지 유형별 조립법" 표는 요소 목록이 나오기 전에 쓴 초안이다. 예를 들어 마이페이지는 표에 두 가지만 적혀 있지만 요소 목록에는 열세 부분이 있다. 구조는 요소 목록과 레퍼런스 조사 결과로 다시 정하고, 정한 내용으로 그 표와 "Subpage Components" 절을 고쳐 쓴다. 토큰 값, 모서리·그림자·강조색 규칙, 문구 말투는 바꾸지 않는다.

### 네가 볼 수 없는 결정들

- **지금 운영 중인 사이트는 참고하지 않는다.** `https://noeul.shop`의 하위 페이지와 `~/noeul.shop` 폴더는 열지 않는다. 사장님은 기존 화면에 묶이지 않은 새 디자인을 원한다. 기존 배치를 한 번 보면 그 구조를 따라가게 되기 때문에 요소 목록도 배치를 빼고 만들었다. 요소 목록만으로 기능이 이해되지 않는 항목은 가장 무난한 해석으로 만들고 `spec/questions.md`에 적는다.
- **홈 시안은 고치지 않는다.** `index.html`과 기존 `css/`·`js/` 파일은 읽기만 한다. 헤더·메뉴·푸터·하단 상담 바는 `DESIGN.md`의 "Page Shell"대로 복사해서 쓴다. 요소 목록의 "사이트 전체 공통 요소"는 대부분 홈 시안이 이미 갖고 있다. 홈 시안에 없는 공통 요소(예: 방문 기록 동의)는 하위 페이지 쪽 공용 부품으로 만들고 보고서에 "홈에도 넣어야 함"으로 적는다.
- **네가 주인인 파일.** 새로 만드는 하위 페이지 HTML, `css/sub.css`, 하위 페이지용 JS, `spec/`·`research/`·`review/`·`tools/` 폴더는 네가 주인이고 앞으로도 네가 관리한다. 같은 스타일을 페이지마다 다시 쓰지 말고 `css/sub.css`의 공용 부품으로 모은다. 새 부품을 만들면 `DESIGN.md` "Subpage Components"에 "(파생)" 표시와 함께 적는다.
- **사장님의 취향.** 국내 대기업 사이트처럼 깔끔하고 세련된 인상을 원한다. AI가 만든 티가 나면 안 된다. 지금까지 싫다고 한 것: 갑자기 나오는 검은 섹션 배경, 뜬금없이 큰 글자, 장식용 단계 번호, 회색 빈 상자로 남긴 자리, 자동으로 흘러가는 띠, 높이가 들쭉날쭉한 카드, 모바일에서 끝없이 긴 스크롤. 반대로 "너무 깔끔해서 밋밋하다"는 말도 했다. 장식을 더하라는 뜻이 아니다. 사진, 글자 위계, 정보 밀도로 완성도를 내라는 뜻이다.
- **지난 리디자인이 나빴던 이유.** 사장님 평가는 "어색하고 빈약했다"였다. 원인은 다섯 가지다. 레퍼런스를 눈으로 보지 않고 기억으로 썼다. 방향을 형용사로만 정했다. 회색 상자와 임시 문구를 남겼다. 빈 상태·오류 같은 상태 화면을 빠뜨렸다. 만든 화면을 스스로 확인하는 절차가 없었다. 이번 작업 순서는 이 다섯 가지를 막도록 짰다.
- **사장님은 Mac Safari(화면 폭 약 1710px)로 본다.** 확인은 Chromium과 WebKit 둘 다로 한다. 세로 flex 안에서 `aspect-ratio` 칸에 좌우 margin을 주고 stretch시키는 조합은 그 Safari에서 어긋난 적이 있으니 쓰지 않는다(폭을 `calc`로 직접 준다).
- **`frontend-design` 같은 디자인 스킬**은 새 미감을 정할 때 쓰는 것이다. 여기서는 미감이 `DESIGN.md`로 이미 정해져 있으니 색·글꼴·분위기를 새로 고르지 않는다.

## 3. 레퍼런스 조사

목적은 "이 유형의 페이지를 잘 만든 곳은 구조와 흐름을 어떻게 풀었는가"를 실제 화면으로 확인하는 것이다. 보기 좋은 그림을 모으는 일이 아니다.

**어디서 찾나.** 디자인 어워드(Awwwards, CSS Design Awards, FWA, Webby, 국내 GDWEB·웹어워드코리아·디비컷), 화면 패턴 모음(Mobbin, Page Flows, Refero처럼 로그인 없이 보이는 범위), 사용성 근거(Baymard Institute와 Nielsen Norman Group의 공개 글), 그리고 실제 운영 중인 사이트를 직접 연다. 한글 화면의 글자 조판을 봐야 하므로 국내 사이트를 반드시 섞는다.

**무엇을 고르나.** 아래를 함께 만족하는 곳을 고른다.
- 우리 페이지와 같은 유형이다(상품 목록, 상품 상세, 장바구니·결제, 긴 입력 양식, 계정 화면, 고객센터·게시판, 문서 화면 등).
- `DESIGN.md` "Overview"의 인상(흰 바탕, 검정 잉크, 사진이 이끄는 깔끔한 패션 커머스, 장식 최소)과 어울린다. 홈 시안을 먼저 렌더링해서 눈으로 본 뒤 고른다.
- 우리만의 어려운 문제를 푼 곳을 유형마다 꼭 포함한다. 색상·사이즈별 대량 수량 입력, 견적 요청형 장바구니, 인쇄·자수 선택과 파일 첨부, 시안 확인과 승인, 사업자 회원 가입, 주문 진행 상태 추적이 그런 문제다. 단체복·유니폼 주문 제작 서비스, 기업 구매몰, 패션 커머스, 대기업의 계정·고객센터 화면에서 찾는다.
- 지금 열리고, PC와 모바일 화면을 둘 다 볼 수 있다.

**얼마나.** 유형마다 후보를 넉넉히(여덟 곳 안팎) 훑고, 그중 세 곳에서 다섯 곳을 남겨 깊게 본다.

**반드시 눈으로 본다.** 남긴 곳은 Playwright로 PC(1440)와 모바일(390) 화면을 캡처해 `research/refs/<유형>/`에 저장하고, 그 그림을 직접 열어 본 뒤에 적는다. 자동 접속이 막힌 곳은 기억으로 쓰지 말고 다른 곳으로 바꾼다. 페이지당 한두 번만 열고, 로그인·양식 제출은 하지 않는다. 외부 서비스에 사장님이나 회사의 이름·이메일·연락처를 보내지 않는다.

**어떻게 적나.** `research/refs/<유형>/notes.md`에 곳마다 주소, 본 날짜, 캡처 파일, 관찰한 사실(정보 순서, 열 수, 입력 방식, 단계 수, 모바일에서 달라지는 점), 우리가 가져올 것·바꿔서 쓸 것·쓰지 않을 것과 이유를 적는다. "세련됨", "신뢰감" 같은 형용사로 끝내지 않는다. "수량 입력을 색상 행 × 사이즈 열 표로 둔다"처럼 그대로 만들 수 있는 문장으로 적는다.

**어디까지 가져오나.** 구조, 흐름, 조작 방식만 가져온다. 색·글꼴·모서리·그림자는 `DESIGN.md` 값만 쓴다. 레퍼런스의 사진·문구·로고는 가져오지 않고, 한 곳을 통째로 따라 하지도 않는다.

**결정으로 마무리한다.** 유형마다 `research/decisions/<유형>.md`를 쓴다. 구조 후보를 두세 개 세우고 하나를 고른 뒤 근거를 적는다. 근거는 레퍼런스에서 관찰한 사실, 요소 목록의 요구, `DESIGN.md` 규칙 세 가지에서 나와야 한다. 문서 제목과 문장은 무엇을 다루는지 그대로 쓰는 평문으로 한다.

## 5. 작업 순서

**0단계: 파악.** `CLAUDE.md`, `DESIGN.md`, `spec/page-elements.md`를 읽는다. 홈 시안을 네 폭(1440·1024·768·390)으로 렌더링해 캡처하고 직접 본다. 이 폴더가 git 저장소가 아니면 `git init`을 하고(용량이 큰 `media/`는 제외) 지금 상태를 첫 커밋으로 남긴다.

**1단계: 페이지 지도.** 페이지를 유형으로 묶는다(상품 목록형, 상세·구매형, 장바구니·결제형, 입력 양식형, 계정형, 게시판·콘텐츠형, 문서형, 결과·안내형 등. 네가 더 맞게 나눠도 된다). `spec/plan.md`에 페이지 → 유형 → 파일 → 상태 목록을 적는다. `spec/coverage.json`을 만든다. 요소 목록의 모든 요소 줄을 항목으로 넣고, 항목마다 어느 파일의 어느 상태, 어느 CSS 선택자에 있는지와 진행 상태를 적는 파일이다.

**2단계: 레퍼런스 조사.** 3절대로 유형별로 조사하고 결정 문서를 쓴다. 유형별 조사는 서로 독립이라 하위 에이전트에 나눠 맡겨도 좋다. 맡길 때는 3절의 기준과 저장 위치를 그대로 전하고, 결정 문서는 캡처를 네가 직접 본 뒤에 네가 쓴다.

**3단계: 유형별 대표 페이지.** 유형마다 한 페이지를 골라 상태까지 완성한다. 이때 그 유형의 공용 부품이 `css/sub.css`에 정리된다. 6절의 확인을 통과하고 독립 검수까지 받은 뒤 다음 유형으로 간다. 대표 페이지가 모이면 `review/golden.html`에 네 폭 캡처를 모아 둔다. 사장님이 중간에 들어와 방향을 볼 수 있게 하는 용도이고, 기다리지 말고 계속 진행한다.

**4단계: 나머지 페이지.** 대표 페이지의 부품으로 같은 유형의 나머지를 만든다. 페이지 제작은 하위 에이전트에 나누지 말고 네가 순서대로 한다. 모든 페이지가 `css/sub.css` 하나를 같이 쓰기 때문에 여럿이 동시에 고치면 서로 덮어쓰고 페이지마다 모양이 조금씩 달라진다.

**5단계: 전체 점검과 보고.** 6절의 확인을 전체 페이지에 돌리고, 7절의 결과물을 마무리한다.

**진행 기록.** 한 묶음이 끝날 때마다 커밋하고(메시지는 한국어로, 무엇을 왜), `spec/progress.md`에 끝난 것·다음 할 것·알아 둘 것을 적는다. 대화가 길어져 앞 내용이 요약되면 `spec/progress.md`, `spec/coverage.json`, `git log`를 다시 읽고 이어 간다.

**채울 내용.**
- 버튼·라벨·안내·빈 상태·오류 문구는 실제로 쓸 최종 문구로 쓴다. 말투는 `DESIGN.md`의 "문구 톤"대로다.
- 상품 사진·이름·가격은 이 폴더의 실제 자료(`js/catalog.js`, `js/brands.js`, `js/reviews.js`, `img/products`, `img/brandp`, `img/reviews` 등)를 쓴다. 회사 정보는 `index.html` 푸터에 있는 값을 쓴다.
- 운영하면서 채워질 자리(주문 내역, 공지 제목, 문의 글, 약관 본문 등)는 그럴듯한 예시 값을 넣고 요소에 `data-sample`을 붙인다. 회사에 대한 새 사실(수치, 실적, 인증, 납기, 할인율, 후기)은 만들지 않는다. 요소 목록에 적힌 조건(파일 개수·용량 제한 등)은 그대로 쓴다.
- 사진이 필요한데 자료가 없으면 회색 상자로 두지 말고 `DESIGN.md` "Asset Conventions"의 `data-slot` 규칙으로 표시하고, 그 자리가 비어 보이지 않게 구성한다.

**멈추지 않고 진행해도 되는 일.** 이 폴더 안에서 파일을 만들고 고치는 것, 웹 검색과 레퍼런스 사이트 열람·캡처, Playwright 실행, 이 폴더 안의 git 커밋. 오류·시간 초과·막힌 사이트 같은 흔한 장애는 원인을 보고 다른 방법으로 넘어간다. 남은 일을 나열하고 멈추거나 "계속할까요"라고 묻지 말고 다음 묶음으로 넘어간다. 이 폴더 밖의 파일을 고치는 일, 어딘가에 올리거나 배포하는 일, 홈 시안 파일을 지우거나 고치는 일은 하지 않는다.

## 6. 확인 방법

"다 됐다"는 아래가 통과했다는 뜻이다. 확인은 스크립트로 만들어 `tools/`에 두고, 페이지를 만들 때마다 돌린다.

1. **화면 점검 스크립트.** 모든 페이지와 모든 상태를 Chromium 네 폭(1440·1024·768·390)과 WebKit 두 폭(1710·390)으로 렌더링해 `review/shots/`에 캡처한다. 가로 스크롤이 생기거나, 콘솔 오류가 있거나, 깨진 이미지가 있거나, `h1`이 하나가 아니거나, 헤더·푸터 블록이 `index.html`과 다르거나, CSS 순서가 "Page Shell"과 다르면 실패로 끝난다.
2. **요소 점검 스크립트.** `spec/coverage.json`의 모든 항목이 완료 상태이고, 적어 둔 선택자가 그 페이지의 그 상태에 실제로 있는지 확인한다. 요소 목록에 있는데 `coverage.json`에 없는 줄이 있어도 실패다.
3. **눈으로 보기.** 스크립트가 통과해도 캡처를 직접 열어 본다. 홈 캡처와 나란히 놓고 같은 사이트로 보이는지, 섹션 간격·제목 구조·정렬선이 홈과 같은지, 한 화면에 강조 버튼이 하나인지, 카드 높이가 고른지, 모바일이 촘촘하고 지나치게 길지 않은지, 2절의 "싫다고 한 것"이 없는지 본다. 어색한 곳은 고치고 다시 캡처한다. 움직이는 요소는 캡처 비교를 반복하지 말고 멈춘 상태로 한 번만 본다.
4. **`DESIGN.md` 점검.** "Generation Checklist" 열 항목을 페이지마다 확인한다. `DESIGN.md`를 고쳤으면 `npx @google/design.md lint DESIGN.md`를 돌려 새 오류가 없는지 본다.
5. **독립 검수와 채점.** 만든 과정을 보지 않은 하위 에이전트에게 `DESIGN.md`, 그 페이지의 요소 목록, HTML, 캡처만 주고 검수시킨다. 항목은 다섯 가지다: 요소가 빠짐없이 있는가, 상태 화면이 다 있는가, `DESIGN.md` 규칙을 지켰는가, 홈과 한 사이트로 보이는가, PC와 모바일에서 깨지거나 어색한 곳이 없는가. 항목마다 0~1000점과 캡처 근거를 받는다. 800점 미만 항목은 고치고 그 항목만 다시 채점받는다. 검수자에게는 점검 스크립트 결과를 먼저 주고 "도구 15회 이내"로 범위를 정해 준다. 취향 차이는 지적 대상이 아니고, 규칙 위반과 눈에 보이는 문제만 받는다.

## 7. 결과물

- 4절의 페이지 파일 전부, `css/sub.css`, 하위 페이지용 JS.
- **`pages.html` — 검수용 목록.** 모든 페이지와 각 상태로 가는 링크를 묶음별로 모은 페이지다. 사장님이 여기서 하나씩 눌러 본다. 상태를 바꿔 보는 방법(예: 주소 뒤 `?state=empty`)은 네가 정하되 이 목록에서 전부 갈 수 있어야 한다.
- `research/`(레퍼런스 캡처, 기록, 유형별 결정), `spec/plan.md`, `spec/coverage.json`, `spec/progress.md`, `spec/questions.md`, `review/`(캡처, 대표 페이지 모음, 채점표), `tools/`(점검 스크립트).
- 고쳐 쓴 `DESIGN.md`("Subpage Components"와 "페이지 유형별 조립법").

**마지막 보고.** 한국어 평문으로, 결과부터 쓴다. 읽는 사람은 작업 과정을 보지 못했다. 다음을 담는다: 어디를 열면 되는지(`pages.html` 경로), 만든 페이지 수와 상태 수, 점검 스크립트 실행 결과와 채점표 요약, 유형별로 어떤 구조를 왜 골랐는지 한두 문장씩, 못 한 것과 확인하지 못한 것, 사장님이 정해야 하는 것(`spec/questions.md`), 홈 시안에 추가가 필요한 공통 요소. 구호 같은 제목이나 멋 부린 문장은 쓰지 않는다.
